# 설계 문서 — CapCut 파리티 및 버그 수정

## 개요

`requirements.md`의 16개 요구사항을 구현하기 위한 설계다. 기존 아키텍처를 최대한 재사용하고 새 병렬 체계를 만들지 않는 것이 지배 원칙이다.

설계 판단의 근거는 코드 직접 확인이다. 빌드·테스트는 실행하지 않았다.

- **네트워크 접근 없음.** `MovieCutMac.entitlements`에 네트워크 entitlement가 없다.

## 2. 검증 정책 — 다른 요구사항의 선행

요구사항 2와 픽셀 판정 기준은 기능이 아니라 **다른 요구사항의 판정 기준**이다. 요구사항 4·7·8·12·15가 여기에 매달려 있으므로 먼저 확정한다.

### 2.1 파리티 게이트 (요구사항 2)

#### 현재 커버리지 실사 (코드 확인)

`scripts/run_core_editing_parity.sh`와 `scripts/verify_preview_export_parity.py`를 직접 읽었다.

**이미 있는 것**
- 하니스가 preview 프레임을 덤프하고(`MOVIECUT_UITEST_PREVIEW_DUMP`) export를 만들고(`MOVIECUT_UITEST_EXPORT`), 스크립트가 동일 timestamp를 MAD로 비교한다
- 시나리오 **7종이 실제로 돈다**: 2x 분할 / 속도 램프 / 텍스트 / BGM / 필터+마스크+자막 / 이미지+비디오 혼합 / 삭제
- 240초 워치독, 실패 시 작업 디렉토리 보존, 프레임 누락은 FAIL (무음 skip 없음)
- `probe_duration()`으로 요청 timestamp의 범위 초과를 가드

**요구사항 2의 수용 기준과 대조한 격차**

| 항목 | 현재 | 격차 |
|---|---|---|
| split | ✅ `split_2x` | — |
| 배속 · 램프 | ✅ `speed_ramp` | — |
| trim | ❌ 없음 | 신규 |
| move | ❌ 없음 | 신규 |
| delete | 🟡 `normal_delete`가 있으나 **실제 갭을 만들지 않는다** — 스크립트 주석이 밝히듯 `deleteClip()`이 항상 선택된(마지막) 클립을 지운다 | 비후행 삭제를 위한 하니스 변경 |
| ripple | ❌ 없음 | 신규 |
| 역재생 · 프리즈 | ❌ 없음 | 신규 |
| undo 왕복 | ❌ 없음 | 신규 |
| 전환 (two-source) | ⛔ **의도적 제외** — 헤드리스에서 앱이 `buildComposition`에서 멈춘다. 대신 `TransitionPixelProcessorTests`가 소프트웨어 렌더러로 픽셀 경로를 덮는다 | 호스트 제약. 해결 대상 아님 |
| duration 단언 | ❌ 범위 가드만 있고 합성 길이 일치 단언은 없음 | 신규 |
| 허용 오차 | ⚠️ 스크립트 기본값 8.0인데 **7종 전부가 25.0을 넘겨 쓴다.** 정당화 기록 없음 | §2.2 |

#### 순환 논리 해소

초안은 "요구사항 2 통과"를 요구사항 4·7·8의 선행으로 뒀다. **이것은 순환이다.** 완전 커버리지는 신규 시나리오 6종 + 하니스 변경을 포함하는 큰 작업이고, 그것이 끝날 때까지 신규 기능이 전부 막힌다. 둘로 쪼갠다.

**2a — 기준선 확립 (요구사항 4·7·8의 실제 게이트)**
- **커버리지를 늘리지 않는다.** 현재 7종을 그대로 실행해 **실측치를 기록**한다.
- 허용 오차 정책을 확정한다 (§2.2). 25.0이 정당한지를 실측 MAD로 판단한다.
- `--expect-duration`과 하니스의 합성 길이 리포트를 추가하고 기존 7종에 적용한다.
- 전환 시나리오의 헤드리스 제약을 **제약으로 명시 기록**하고 해결 대상에서 뺀다.
- **여기까지가 게이트다.** 이 시점에 "무엇이 현재 어긋나 있는가"가 수치로 확정된다.

**2b — 커버리지 확장 (요구사항 4·7·8의 선행이 아니다)**
- trim / move / ripple / 역재생 / 프리즈 / undo 왕복 시나리오 신규
- 비후행 클립 삭제를 위한 하니스 변경
- 요구사항 4·7·8과 **병행한다.** 각 기능은 자기 시나리오를 2a가 세운 틀에 추가한다.

**2a에서 기준선이 red면?** 그것이 이 요구사항의 존재 이유다. 실패 항목 수리가 2a의 일부이고, 범위가 크면 별도 항목으로 승격한다. **게이트를 통과시키려고 허용 오차를 올리는 것은 금지한다.**

#### 설계

1. **하니스가 기대 길이를 리포트한다.** 기존 `parity_done` / `error=none` 키=값 리포트 형식을 따른다.
2. **`--expect-duration` 옵션 추가.** 주어지면 `probe_duration()` 결과와 1프레임(프로젝트 frameRate) 이내인지 확인. 없으면 현행 동작 유지 → 기존 호출부 무회귀.
3. **undo 왕복은 픽셀이 아니라 상태 비교다.** `Project`가 `Equatable`이므로 모델 수준에서 직접 비교한다.
4. **기존 규율 유지.** 신규 시나리오도 같은 `run_scenario` 함수를 쓴다.

### 2.2 픽셀 판정 정책 (요구사항 4·12·15의 선행)

**서로 다른 두 척도가 이미 저장소에 있고, 초안은 이를 구분하지 않은 채 골든 픽셀 의존을 키웠다.**

| 척도 | 위치 | 단위 | 현재 값 |
|---|---|---|---|
| 골든 픽셀 (채널별) | `GoldenPixel.expectClose` | 채널당 절대 오차 | 기본 `tolerance: 2` |
| 렌더러 생존 확인 | `GoldenPixel.assertRendererFunctional` | 채널당 절대 오차 | 중간 회색 sentinel ±6 |
| 프레임 비교 | `verify_preview_export_parity.py` | 프레임 전체 MAD (0~255) | 스크립트 기본 8.0 / **실사용 25.0** |

**기준 머신 정책은 이미 확립되어 있다 — 새로 정의하지 않는다.** `GoldenPixel.context`는 `useSoftwareRenderer: true`인 `CIContext`다. 골든의 기준은 특정 물리 머신이 아니라 **소프트웨어 렌더러**이며, 이것이 headless에서 픽셀 단언이 무음 skip되던 문제를 해결한 선례다. 새 골든도 반드시 이 컨텍스트를 쓴다. GPU 컨텍스트로 골든을 만들면 머신 의존이 생긴다.

**skip ↔ fail 분기도 이미 결정되어 있다.** `assertRendererFunctional()`이 sentinel 실패를 **fail**로 만든다. skip은 어떤 경우에도 허용하지 않는다.

**결정**

1. **신규 골든 테스트(요구사항 4·15)는 `expectClose` 기본 오차 2를 쓴다.** 더 큰 값이 필요하면 해당 테스트에 한해 근거를 주석으로 남긴다. **전역 기본값을 올리지 않는다.**
2. **`assertRendererFunctional()`을 모든 신규 골든 테스트 최상단에서 호출한다.** 예외 없다.
3. **preview↔export MAD 25.0은 2a에서 재검토한다.** 골든 오차 2와 **같은 척도가 아니다** — 프레임 전체 평균이고 인코딩 손실·스케일·패딩이 섞인다. 다만 기본값의 3배이며 정당화 기록이 없다. 실측 분포를 보고 (a) 낮출 수 있는 시나리오는 낮추고 (b) 25.0이 필요하면 이유를 기록한다.
4. **iOS↔macOS 비교(요구사항 12·13)에 골든 척도를 쓰지 않는다.** 두 플랫폼은 서로 다른 Core Image/Metal 경로를 탈 수 있고, 매트 연산(edgeShrink/softness)의 부동소수 연산 순서가 달라 **픽셀 1:1 불일치가 정상이다.** 채널당 ±2를 요구하면 요구사항 12의 "완료"가 기기 조합에 따라 흔들린다. 따라서:
   - 판정은 **MAD 척도**로 하고, 허용 오차는 2a가 확정한 같은 기기 기준선과 **같은 값**에서 출발한다.
   - 비교는 **고정된 시뮬레이터 기종·OS 버전 1종**에서 수행하고 그 조합을 결과에 기록한다. 기종을 바꾸면 값이 달라질 수 있으므로 기록 없는 수치는 무효다.
   - 오차 초과는 "테스트 실패"가 아니라 **파리티 격차 보고 대상**이다. 수치와 함께 원인(연산 순서 / 실제 로직 차이)을 구분해 기록한다.
   - **이 결정은 `requirements.md` 요구사항 12의 수용 기준 3 문구("픽셀 수준에서 일치")와 어긋난다.** §9에 반영 필요 항목으로 올렸다.
5. **오차 상향은 변경이 아니라 결정이다.** 커밋 메시지와 문서에 근거를 남긴다.

### 2.3 검증 인프라 실존 확인 (착수 0단계)

여러 요구사항이 "기존 하니스로 승격한다"고 말하는데, 그 하니스가 실제로 존재하고 도는지는 별개 문제다. 착수 첫 작업에서 확인한다.

| 인프라 | 실존 여부 (이 설계에서 확인) | 남은 확인 |
|---|---|---|
| 접근성 레이블을 읽는 테스트 경로 | ✅ 존재 — `App/MovieCutMacUITests/`, `CardEditorUITests`가 `XCUIElement.label`을 읽는 `waitForLabel` 헬퍼를 가짐 | 이 호스트에서 XCUITest가 실제로 완주하는가 |
| 골든 픽셀 하니스 | ✅ 존재 — 소프트웨어 렌더러 + `assertRendererFunctional()` | 이 호스트에서 sentinel이 통과하는가 (실패 시 요구사항 4·15의 검증 수단이 없다) |

**확인된 제약 (설계에 영향):** `UnsavedChangesGuardUITests`의 주석에 따르면 `MOVIECUT_UITEST_QUIT`을 설정하면 앱이 결과 기록 직후 종료되어 **XCUIApplication의 접근성 핸드셰이크가 깨진다**("has not loaded accessibility"). 따라서 접근성을 읽는 테스트는 `QUIT`을 켜지 않고 앱을 살려둔 채 검사해야 한다. 요구사항 1의 검증이 이 제약을 따른다.

**두 하니스 중 하나라도 이 호스트에서 못 돌면, 그 인프라 구축이 해당 요구사항(1 또는 15)의 범위 안이다.** 검증 수단 없이 기능을 완료로 표시하지 않는다.

### 스키마 통합 메커니즘 — 번호 충돌을 구조적으로 없앤다

초안은 "병합 시점에 번호를 재부여"라고만 했다. 그것은 병합자의 수작업에 의존하고, 특성 브랜치가 마이그레이터를 짜려면 부착할 번호가 이미 필요하므로 실행이 불가능하다. 다음으로 대체한다.

**1단계 — 특성 브랜치 (요구사항 4·5·7 각각)**
- 필드만 추가한다. `decodeIfPresent ?? 기본값` + 기본값이 아닐 때만 encode.
- **`currentSchemaVersion`을 건드리지 않는다. 마이그레이터를 만들지 않는다.**
- 필드가 없는 기존 프로젝트가 열리는지 픽스처 테스트로 고정한다. 이것은 버전 번호와 무관하게 성립한다 — additive 필드의 하위호환은 디코더가 보장한다.

**2단계 — 단일 "스키마 통합" 작업 (특성들이 모두 병합된 뒤 한 번)**
- 그 시점에 합쳐진 필드 전체를 대상으로 `currentSchemaVersion`을 한 번 올리고 항등 마이그레이터 하나를 등록한다.
- 체인이 `currentSchemaVersion`에 도달하는지 확인하는 테스트를 통과시킨다.

**왜 안전한가:** 세 필드 모두 항등 마이그레이션이다. 즉 버전 번호가 늦게 붙어도 데이터 손실 경로가 없다. `ProjectMigrationRunner`의 불완전 체인 loud-fail은 안전망으로 남지만, **안전망에 기대지 않고 충돌 자체를 없앤다.**

## 4. 요구사항별 설계

### 4.1 접근성 레이블 현지화 (요구사항 1)

**선택: 근본 수정.** 한국어 키를 영어 키로 바꾼다. 카탈로그 `sourceLanguage`가 `en`인데 키가 한국어인 것이 원인이고, `en` 값 3건만 채우는 최소 수정은 같은 실수의 재발을 막지 못한다.

- 대상: `NSLocalizedString` 키가 한국어인 호출부 전체 (`TimelineView.swift:788, 941, 950` 포함)
- 카탈로그 키를 재정렬하고 **코드 사용 키 ↔ 카탈로그 키 대조 스크립트**로 누락을 확인한다. 손으로 세지 않는다.
- **깨지는 기존 테스트:** `R504MainVideoTrackStaticContractTests`, `R503TrackHeaderStaticContractTests`, `UIUXAccessibilityRegressionStaticContractTests`가 한국어 키 문자열을 직접 단언한다. 요구사항 15를 기다리지 않고 **이 작업 안에서** 처리한다 (미루면 main이 빨간 상태로 남는다).
- **승격 경로는 실존한다** (§2.3). `XCUIElement.label`을 읽는 `waitForLabel` 헬퍼가 이미 있다. 접근성 회귀 방지가 목적인 단언은 여기로 옮긴다.
- **제약 준수:** 접근성을 읽는 테스트는 `MOVIECUT_UITEST_QUIT`을 켜지 않는다 (§2.3).

### 4.2 홈 화면 (요구사항 3)

App 계층에 `AppStage` (`.home` / `.editor`)를 두고 `MovieCutMacApp`의 `WindowGroup`에서 분기한다.

```
MovieCutMacApp
  └─ WindowGroup
       ├─ AppStage.home    → HomeView (신규)
       └─ AppStage.editor  → ContentView (기존, 무변경)
```

**신규 파일**
- `App/MovieCutMac/Home/RecentProjectsStore.swift`
- `App/MovieCutMac/Home/HomeView.swift`

**`SecurityScopedAccess` 재사용 범위 — 정정.** 이 타입은 `MediaAsset`에 결합되어 있다. `resolveBookmark(for: asset)` / `beginScope(for: asset)` / `withSecurityScope(for: asset)` 전부 asset을 받고, URL을 받는 것은 `makeBookmark(for url:)` 하나뿐이다. 따라서:

| 필요한 것 | 재사용 가능? |
|---|---|
| 프로젝트 파일 URL의 bookmark 생성 | ✅ `makeBookmark(for:)` 그대로 |
| bookmark 해결 + stale 검출 + 스코프 시작/종료 | ❌ **asset 결합. URL 수준으로 일반화가 필요하다** |

즉 "기존 것을 재사용한다"는 표현은 부정확했다. **`resolveBookmark` / `beginScope` / `endScope`의 URL 오버로드를 추가하고 기존 asset 버전이 그것을 호출하도록 리팩터**한다. 로직을 복제해 두 번째 bookmark 처리 경로를 만들지 않는다 — 그 파일의 주석이 스스로 "이 라이프사이클의 단일 소유자"라고 선언하고 있고, 그 성질을 깨지 않는다.

**E2E 무회귀 게이트.** `MOVIECUT_BOOTSTRAP_PROJECT` 또는 `MOVIECUT_UITEST`가 설정되면 홈을 건너뛰고 편집기로 직행한다. 두 분기는 `MovieCutMacApp`에 이미 있다.

**⚠️ 이 게이트가 만드는 커버리지 사각지대.** 하니스가 홈을 정확히 우회하므로, **이번에 새로 추가되는 것(AppStage 분기, 홈 진입, dirty 저장 확인)이 기존 E2E로는 전혀 검증되지 않는다.** 따라서:
- `AppStage` 전이 로직을 **뷰에서 분리한 순수/테스트 가능 타입**으로 만든다 (홈 표시 여부 결정, dirty 시 전이 차단, 하니스 게이트 판정).
- 그 타입의 **단위 테스트**로 전이·게이트·dirty 분기를 덮는다. `RecentProjectsStore` 테스트만으로는 라우팅이 커버되지 않는다.
- 홈을 **거쳐서** 편집기에 도달하는 XCUITest 1건을 별도로 둔다 (게이트 환경변수를 켜지 않은 경로).

**저장 확인.** `MovieCutAppDelegate.applicationShouldTerminate`의 3버튼(Save / Don't Save / Cancel) 정책을 그대로 따른다. 같은 상황에 다른 UX를 만들지 않는다.

**썸네일.** 기존 `ThumbnailGenerator`로 저장 시점에 1장 기록.

### 4.3 블렌딩 모드 (요구사항 4)

**신규 `Sources/MovieCutCore/Rendering/BlendPixelProcessor.swift`** — 두 `CIImage`와 모드를 받아 합성한다. `VisualEffectPixelProcessor`가 내부적으로 쓰는 `CISoftLightBlendMode` 등을 사용자 노출 개념으로 승격한다.

배선 지점은 다중 트랙 합성 경로다. macOS `CustomVideoCompositor`, iOS `IOSCustomVideoCompositor`. UI는 `InspectorBasicSection` 드롭다운, 명령은 기존 `SetClipPropertyCommand` 재사용.

**회귀 방어.** `.normal`은 프로세서를 **호출하지 않고 우회**한다. 통과시키면 색공간 왕복으로 미세한 차이가 생겨 "도입 전후 픽셀 동일" 기준이 깨진다.

**⚠️ 크로스 플랫폼 완료는 요구사항 12에 종속된다.** iOS 합성기는 현재 공유 프로세서를 경유하지 않고 inline 재구현을 쓴다. 즉 iOS에 블렌딩을 넣으려면 요구사항 12의 공유 프로세서 마이그레이션이 선행이어야 하고, 그것은 iOS 플랫폼 설치에 막혀 있다. **따라서 요구사항 4는 macOS 범위에서 완료하고, iOS 블렌딩은 요구사항 12 이후로 명시 이관한다.** macOS만 된 상태를 "완료"로 적을 때 그 한계를 함께 적는다.

**⚠️ 헤드리스 제약 가능성.** 전환 시나리오가 `buildComposition`에서 멈추는 것과 같은 이유로, 다중 트랙 블렌딩의 앱 레벨 파리티 검증이 막힐 수 있다. 그 경우 픽셀 수식은 소프트웨어 렌더러 골든으로 덮고(전환이 이미 그렇게 처리됐다) 앱 레벨 제약을 기록한다. 은폐하지 않는다.

### 4.4 프리뷰 품질 (요구사항 5)

`PlaybackSettings`에 `previewQuality`를 추가한다. 프록시 설정 3종이 이미 여기 있다.

**적용 지점은 `PlaybackEngine`의 렌더 해상도뿐이다.** `ExportEngine`은 `project.canvas`를 쓰므로 export 해상도는 정의상 영향을 받지 않는다.

**⚠️ 배지 상태의 조합성 문제.** 화질 저하 원인이 셋으로 늘어나는데(수동 프록시 / 열 강등 / 수동 프리뷰 품질) **서로 배타적이지 않다.** 열 강등 중에 사용자가 프리뷰 품질을 낮춰 둘 수도 있다. `ProxyBadgeState`는 단일 값 enum이라 조합을 담지 못한다.

**결정: 배지는 우선순위 단일 표시, 상세는 보조 텍스트.**
- 표시 우선순위: 열 강등 > 수동 프록시 > 수동 프리뷰 품질. 자동 강등이 가장 설명이 필요하기 때문이다 (이유 없는 화질 저하는 버그로 읽힌다).
- 동시에 걸린 원인 전체는 배지의 **접근성 레이블 / 툴팁 문자열**에 담는다.
- 배지에 아이콘을 겹쳐 그리지 않는다. 작은 표면에 두 글리프를 겹치면 어느 것도 읽히지 않는다.
- 우선순위 결정 함수는 Core에 순수 함수로 두고 조합 케이스를 단위 테스트한다. `ProxyBadgeState.resolve`가 이미 그 자리에 있다.

### 4.5 자막 포맷 확장 (요구사항 6)

`SubtitleDocument.swift`에 `srtString(from:)` / `parseSRT` / `srtTimestamp(from:)`가 이미 있다. 같은 파일에 `vttString(from:)` / `assString(from:)`을 추가한다.

- WebVTT: `WEBVTT` 헤더 + `HH:MM:SS.mmm` (SRT의 콤마와 다르다)
- ASS: `[Script Info]` / `[V4+ Styles]` / `[Events]` 섹션 + `H:MM:SS.cc` (센티초)

**스코프 못 박기 — 텍스트와 타이밍만 한다. 스타일링은 범위 밖이다.** ASS는 폰트·색·외곽선·위치·카라오케 태그(`\k`)까지 표현할 수 있는 포맷이라, 명시하지 않으면 스코프 크리프가 사실상 확정이다. `[V4+ Styles]`에는 **단일 기본 스타일 하나만** 쓰고 클립별 텍스트 스타일을 매핑하지 않는다. 워드 타이밍의 `\k` 태그도 하지 않는다 (필요해지면 별도 항목).

UI는 `AutoSubtitlesView.exportSRT()`를 포맷 선택으로 확장한다. `srtString`은 손대지 않는다.

### 4.6 컴파운드 클립 (요구사항 7) — 이 스펙에서 가장 큰 항목

#### 모델: 참조 방식 (재귀 중첩 아님)

| 안 | 내용 | 판정 |
|---|---|---|
| A | `Clip`에 중첩 `Timeline`을 직접 embed | **기각** — `Clip` → `Timeline` → `Track` → `Clip` 재귀 Codable이 되고 기존 순회 코드 전반의 재작성을 부른다 |
| B | `Project.compounds`에 정의를 두고 `Clip.compoundId`가 참조 | **채택** |

#### 중첩 스코프 — Inc 1은 중첩 불가로 고정한다

참조 모델은 원리적으로 컴파운드 안의 클립이 또 `compoundId`를 갖는 것을 허용하고, 그러면 flatten이 재귀해야 하며 순환(A→B→A) 검출이 flatten 경로에도 필요하다. **Inc 1의 범위를 명시적으로 좁힌다.**

- **Inc 1: 중첩 금지.** `CompoundDefinition`의 자식 클립은 `compoundId`를 가질 수 없다. 생성 시점에 거부하고, 로드 시 발견되면 명시적 오류로 만든다.
- flatten은 **1단계 펼침**이며 재귀하지 않는다. 이 제약 덕분에 순환이 원리적으로 불가능하다 — 순환 검출 코드가 필요 없다.
- 재귀 flatten과 순환 검출은 중첩을 허용할 때 필요해지며, **이 스펙의 범위 밖**이다.

**Inc 1의 정직한 라벨.** CapCut 사용자가 기대하는 컴파운드는 "더블클릭해서 내부를 편집하는 중첩 시퀀스"다. Inc 1이 만드는 것은 **단일 단위로 렌더되는 클립 묶음(슈퍼 그룹)**이며 내부 편집이 없다. 문서·UI·완료 보고에서 Inc 1을 "컴파운드 클립 완성"으로 부르지 않는다.

#### 렌더: 펼쳐서 기존 경로에 넘긴다

새 합성 엔진을 만들지 않는다. 렌더 전에 컴파운드를 펼친 타임라인을 만들어 기존 합성 경로에 넘긴다. Core의 순수 함수로 둔다.

#### ⚠️ flatten 캐시는 단일 출처여야 한다 — 파리티 보장의 전제

"preview와 export가 같은 순수 함수를 통과하므로 일치가 구조적으로 보장된다"는 주장은 **양쪽이 같은 flatten 결과를 공유할 때만 참이다.** `PlaybackEngine`과 `ExportEngine`이 각자 캐시를 들면 무효화 시점이 어긋나는 순간 서로 다른 스냅샷으로 렌더한다 — 그것이 정확히 요구사항 2가 막으려는 preview↔export 괴리의 재현이다.

**설계**

```
Project 변경 (명령 적용 후)
        ↓
flatten() 1회 계산  ← 단일 계산 지점 (App 계층 세션/뷰모델)
        ↓
FlattenedTimeline (값 타입 스냅샷)
        ├──→ PlaybackEngine  (인자로 받는다)
        └──→ ExportEngine    (인자로 받는다)
```

- **두 엔진은 flatten을 호출하지 않는다. 결과를 인자로 받는다.** 엔진 내부에 컴파운드 인지 코드를 두지 않는다.
- 캐시는 **한 곳에만** 존재한다. 프로젝트 변경 시 무효화되고 재계산된다.
- 프레임 루프에서 flatten을 호출하지 않는다 (성능).
- 검증: 같은 프로젝트에 대해 두 엔진이 받은 `FlattenedTimeline`이 동일함을 테스트로 고정한다. `Equatable`이므로 직접 비교할 수 있다. **이 테스트가 파리티 주장의 근거다.**

#### 증분 분리

| 증분 | 내용 | 사용자 노출 | 닫는 수용 기준 |
|---|---|---|---|
| **1a 모델·직렬화** | `CompoundDefinition`, `Project.compounds`, `Clip.compoundId`, 중첩 금지 검증, 깨진 참조 검출 | **없음** | 6 |
| **1b flatten 렌더** | 순수 1단계 flatten + 단일 출처 캐시 + 두 엔진 배선. UI 없이 테스트·하니스로 구동 | 없음 | 5 |
| **1c 편집 UI** | 생성/해제 명령 2종, 타임라인 단일 클립 표시, 이동·트림·복사 시 내부 구성 보존 | 있음 | 1 · 2 · 4 · 7 |
| **2 내부 편집 + 컴파운드 레벨 효과** | 중간 미디어 오프라인 렌더. `ImageVideoRenderService` / `ReverseRenderService` 패턴 복제 | 있음 | 3 |

**1a와 1b는 사용자 노출이 없다.** 여기서 중단해도 사용자에게 보이는 미완성 기능이 남지 않는다 — 가장 안전한 중단 지점이다. UI 표면은 1c에서 처음 생긴다.

**Inc 2는 이 스펙의 필수 완료 조건에서 분리한다.** 재렌더 무효화 정책이라는 열린 결정(§9)에 걸려 있고, 그 결정은 1c까지의 실사용 감각을 보고 내리는 편이 낫다.

#### 명령

컴파운드 생성/해제는 신규 명령 2개. 각각 단일 undo 단위. `GroupClipsCommand`와 복사/붙여넣기의 그룹 id 재매핑이 선행 참고 구현이다.

### 4.7 slip / slide (요구사항 8)

`ClipTrimMath`에 두 순수 함수를 추가한다. 그 파일 주석이 남긴 교훈이 핵심이다 — 과거 트림 제스처가 "타임라인 1초 == 소스 1초"를 가정하고 매핑을 참조하지 않아 램프 클립에서 깨졌다.

- 배속·램프 클립에서 timeline↔source 매핑을 반드시 경유한다.
- 명령 2개 신규. `CommandSupport`의 locked-track 가드 재사용.

### 4.8 보컬 분리 배선 (요구사항 9)

`NoiseReductionService` 배선 패턴을 그대로 복제한다. 모노 입력은 명시적 오류로 실패한다 — 조용히 무처리 통과시키면 사용자가 동작했다고 오해한다.

**검증은 오디오 측정이다.** 센터/사이드 팬 성분을 구분한 fixture로 센터 에너지 감소와 사이드 유지를 수치로 확인한다. 이 서브시스템이 dead code로 남았던 이유가 애초에 그 규율의 부재였다.

### 4.9 서브시스템 정리 (요구사항 10)

#### 0단계 — 삭제 전 참조 재측정 (요구사항 10의 수용 기준 1)

**삭제 전에 각 파일의 현재 참조 상태를 grep으로 재측정하고 결과를 기록한다.** 요구사항 문서의 결정 표는 문서 근거로 작성됐고, 이 저장소는 문서가 낡는 전례가 있다. 표와 실측이 어긋나면 표를 갱신하고 결정을 재검토한다. 이 단계를 건너뛰지 않는다.

#### 삭제 사유 분류 — 사유가 다르면 되돌리는 조건도 다르다

| 서브시스템 | 결정 | 사유 유형 | 되돌릴 조건 |
|---|---|---|---|
| `AI/ClaudeEditingProvider` (+`URLSessionClaudeTransport`) | 삭제 | **구조적 불가** — 네트워크 entitlement 부재로 샌드박스에서 동작 불가 | 제품이 네트워크를 공식 채택 (별도 스펙) |
| `Cloud/CollaborationService` | 삭제 | **구조적 불가** — 원격 상태·공유 링크가 네트워크 필수 | 동일 |
| `Analysis/StyleTransferProvider` | 삭제 | **중복** — 실제 스타일 효과는 `VisualEffectPixelProcessor` 계열이 제공 | 없음 (중복은 되돌릴 이유가 없다) |
| `Analysis/BackgroundRemovalProvider` | 삭제 | **중복 (위양성)** — 기능은 `PersonSegmentationCompositor` 경로로 동작 | 없음 |
| `Cloud/VersionHistory` | 삭제 | **우선순위** — 동작은 가능하나 CapCut 파리티 항목이 아니고 로드맵 슬롯이 없다 | 로컬 버전 관리를 제품이 채택하면 별도 스펙으로 신설 |

**구조적 불가와 우선순위를 구분하는 이유:** 전자는 재론 대상이 아니고, 후자는 제품 판단이 바뀌면 되돌아온다. 한 줄로 묶으면 다음 감사가 다시 물어본다.

`BackgroundRemovalProvider`는 삭제 전에 배경 제거 기능이 여전히 동작함을 먼저 보인다. 위양성이므로 기능 회귀 확인이 삭제의 전제다.

#### 순서

```
0단계  참조 상태 grep 재측정 + 결정 표 대조
   ↓
1단계  삭제 5건 (+ 그것만을 대상으로 한 테스트)
   ↓  빌드 + 전체 테스트 green, 테스트 수 감소 기록
2단계  AIEditingProvider 프로토콜 경유로 어시스턴트 UI 배선
   ↓
3단계  요구사항 9 (보컬 분리)
```

**삭제를 먼저, 배선을 나중에.** 삭제로 테스트 수가 줄고 배선으로 늘어난다. 순서를 섞으면 어느 변화가 어느 작업의 결과인지 판별할 수 없다.

`AIEditingProvider` 배선은 `RuleBasedEditingProvider`가 기존 `AssistantCommandParser` → `AssistantIntent` 경로를 감싸는 형태다. 새 실행 경로가 아니라 기존 경로에 프로토콜 이음새를 끼우는 작업이다.

### 4.10 iOS 트랙 (요구사항 11–14)

**전부 요구사항 11에 막혀 있고, 요구사항 11은 사용자의 플랫폼 설치에 막혀 있다.** 플랫폼이 없으면 코드를 쓸 수는 있어도 컴파일되는지조차 알 수 없다. "코드를 썼다"를 완료로 인정하지 않는다.

```
[사용자 조치: iOS 플랫폼 설치]
   ↓
요구사항 11  iOS 테스트 타깃 + 하니스 진입점
   │         macOS 전례: ContentView의 .task { runUITestHarnessIfRequested() }
   ↓
요구사항 12  IOSCustomVideoCompositor의 inline 크로마키/세그멘테이션을
   │         Core 공유 프로세서 호출로 교체 (inline 구현 제거)
요구사항 13  IOSCustomVideoCompositor에 two-source instruction 경로 추가
   │         macOS 전례: CustomVideoCompositor의 two-source 분기 + :437 프로세서 호출
요구사항 14  iOS 문자열 래핑 → 카탈로그 → 한국어 로케일 실행 확인
   ↓
(이관) 요구사항 4의 iOS 블렌딩 — §4.3
```

- 12와 13은 **같은 파일을 고친다.** 병렬 진행하면 충돌한다. 순차 또는 한 세션.
- 14는 카탈로그가 아니라 **래핑이 선행**이다. iOS 소스에 `NSLocalizedString` 래핑이 확인되지 않았다.
- 12·13의 크로스 플랫폼 판정은 §2.2 결정 4를 따른다 — 골든 척도가 아니라 MAD 척도, 고정 시뮬레이터 1종, 기종 기록 필수.

### 4.11 검증 부채 (요구사항 15) 와 문서 정리 (요구사항 16)

요구사항 15는 세 단계로 쪼갠다.

1. `docs/` 산문 단언 제거
2. 부정 단언 전수 분류 (결함 고정 → 제거 / 경계 방향 → 주석 후 유지)
3. 렌더 프로세서 문자열 단언을 골든 픽셀로 승격

**⚠️ 블랭킷 제거 금지 — 건별 사유를 기록한다.** "테스트 수 감소는 정상"이라는 전제에는 함정이 있다. StaticContract 파일 안에 **드물게 실제 동작을 단언하는 테스트가 섞여 있을 수 있고**, 파일 단위로 휩쓸면 그것까지 사라진다. 그러면 수치상으로는 "가짜 신호 제거"로 보이지만 실제로는 커버리지 손실이다.

- 제거·승격·유지 판정을 **단언 건별로** 기록한다. 파일 단위 일괄 삭제를 하지 않는다.
- 각 건에 (a)삭제 (b)승격 (c)유지 중 무엇이며 근거 한 줄을 남긴다.
- 애매한 건은 애매하다고 표시하고 유지 쪽으로 기울인다.

**승격 대상 하니스 실존 확인은 §2.3에 있다.** 골든 픽셀 하니스가 이 호스트에서 실제로 도는지 확인되지 않으면 3단계는 인프라 구축을 포함한다.

**요구사항 1과의 교차점:** 4.1이 깨뜨리는 접근성 StaticContract는 1단계를 기다리지 않고 요구사항 1 작업 안에서 처리한다.

요구사항 16은 스펙 전체의 마무리다. 각 요구사항이 끝날 때마다 해당 지시서 항목을 근거와 함께 완료 표시하고, 마지막에 최신 판정으로 가는 단일 진입점을 남긴다.

## 5. 오류 처리

새로 만드는 실패 경로는 모두 **명시적 실패 + 사용자에게 보이는 사유**를 원칙으로 한다. 조용한 폴백은 만들지 않는다. STT가 조용히 서버로 폴백하던 것이 반면교사다.

| 상황 | 처리 |
|---|---|
| 최근 프로젝트 파일 없음 / bookmark stale | 목록에서 구분 표시 + 제거 수단. 조용히 숨기지 않는다 |
| 보컬 분리 입력이 모노 | 명시적 오류. 무처리 통과 금지 |
| `compoundId`에 해당 정의 없음 | 로드 시 명시적 오류. 빈 클립으로 조용히 렌더하지 않는다 |
| 컴파운드 자식이 `compoundId`를 가짐 (중첩) | 생성 시 거부, 로드 시 명시적 오류 (§4.6 중첩 금지) |
| 자막 export 대상 세그먼트 없음 | 빈 파일 생성 대신 사유 표시 |
| 스키마 버전이 현재보다 높음 | 기존 `ProjectMigrationError.newerThanCurrent` 경로 (구현됨) |

진단 로깅은 기존 `AppLog.swift` 카테고리 체계를 쓴다. 원격 전송은 추가하지 않는다.

## 9. 열린 항목 및 요구사항 문서에 반영 필요

### 요구사항 문서 수정이 필요한 것

1. **요구사항 12의 수용 기준 3 — "픽셀 수준에서 일치".** §2.2 결정 4에 따라 크로스 플랫폼은 골든 척도로 판정할 수 없다. "고정 시뮬레이터 1종에서 같은 기기 기준선과 동일한 MAD 허용 오차 내"로 문구를 바꿔야 한다. 이 설계가 승인되면 `requirements.md`를 함께 갱신한다.

3. **요구사항 4의 iOS 범위** — macOS 완료 후 iOS는 요구사항 12 이후로 이관됨을 표시한다.
