전체적으로 보면 개발 성숙도는 꽤 높은데, 베타 준비도는 아직 그보다 한 단계 낮습니다. 이유는 기능 개수나 테스트 수가 아니라, 최근 CA-18과 CA-21에서 드러난 것처럼 "검증기가 잘못된 성공을 보고할 수 있다"는 리스크와 실제 배포·실기기·데이터 보존 경로가 아직 완전히 닫히지 않았기 때문입니다.

특히 지금부터는 CapCut 기능을 더 따라가는 것보다 MovieCut을 믿고 프로젝트를 맡길 수 있는가를 증명하는 단계로 전환하는 것이 좋습니다.

## 1. 현재 진행상황에서 보이는 리스크·누락

### 가장 중요한 리스크: 검증 하니스 자체의 신뢰성

이번 보고에서 가장 중요한 신호는 사실 CA-18의 실패율이나 CA-21의 성능 수치가 아닙니다.

- CA-18: 측정기가 거짓 PASS를 만들 수 있었음
- CA-21: 실제 기능은 전 프레임 all-zero인데 기존 구현이 살아 있었음
- 수정하고 나서야 실제 성능 또는 실제 FAIL이 드러남

즉, 현재 MovieCut의 가장 큰 기술 리스크 중 하나는 Feature Defect보다 Oracle Defect, 다시 말해 "틀린 것을 맞다고 판단하는 검증 시스템"입니다.

따라서 verify_gate 위에 사실상 하나의 메타 게이트를 추가하는 것을 권합니다.

**Measurement Qualification Gate** — 각 성능/정확도 하니스는 최소 다음을 만족해야 합니다.

| 항목 | 요구사항 |
|---|---|
| Positive Control | 확실히 PASS해야 하는 입력이 실제 PASS |
| Negative Control | 의도적으로 망가뜨린 구현/입력이 반드시 FAIL |
| Degeneracy Check | all-zero, constant output, empty output 등을 즉시 FAIL |
| Dataset Pinning | 입력 데이터 hash 기록 |
| Harness Pinning | 하니스 코드 commit SHA/hash 기록 |
| Threshold Pinning | 실행 전에 임계값 확정 |
| Clean Re-run | clean checkout에서 동일 결과 재현 |
| Evidence Binding | 결과를 정확한 app SHA + harness SHA에 연결 |

특히 하니스 코드가 수정되면 이전 측정 증거를 자동 STALE 처리하는 규칙이 중요합니다. 예를 들어 CA-21의 기존 PASS 이력이 있었다면 CIAreaHistogram 오류 수정 이후에는 과거 결과를 그대로 유지해서는 안 됩니다.

### P0 — 프로젝트 파일 무결성 / Migration

CA-20에서 스키마가 v9까지 올라왔다는 것이 오히려 중요한 신호입니다. 베타 사용자가 가장 싫어하는 실패는 장면 검출이 조금 틀리는 게 아니라 "어제 편집하던 프로젝트가 오늘 안 열리는 것"입니다.

**ProjectIntegrityGate**: v1~v8 fixture → current v9 loader → migration → save → close → reopen → semantic equality. 그리고 최소한 다음을 자동화:
- 구버전 → v9 migration, migration 2회 실행 시 idempotent
- save 중 강제 종료, 파일 일부 truncate, JSON/DB 일부 corruption
- 미래 버전 프로젝트를 열었을 때 overwrite 금지(fail-closed — "열 수 없음"은 괜찮지만 "일부 읽은 뒤 현재 스키마로 다시 저장"은 프로젝트 손상)
- 프로젝트 파일 read-only, 연결 media 누락, media 위치 변경, external drive 분리 후 재연결 복원
- undo/redo 후 save/reopen 동일 상태

### P0 — verify_gate 4/5를 예외 통과시키지 않는 것

iOS build만 로컬 환경 문제 + push 시 CI 커버 논리는 개발 중에는 괜찮지만 Beta Release Gate로는 부족합니다. 증거 체인: main commit SHA → Remote CI → iOS compile → Archive → Code Signing → TestFlight Upload → Real Device Install → Cold Launch → Import → Edit → Save/Reopen → Export. verify_gate와 별도의 **distribution_gate**를 두고, 실행 불가하면 결과를 BLOCKED로 둘 것. PASS-equivalent로 취급하면 안 됩니다.

### P0 — Export의 "성공 여부"보다 "내용 정확성"

ENOSPC 실측은 좋지만 현재 증거는 "실패했을 때 깨끗하게 실패하는가" 쪽. 영상 편집 앱에서는 "성공했다고 했는데 영상이 틀렸는가"가 더 중요. **ExportIntegrityGate**: duration 차이, 시작/중간/끝 golden frame, A/V sync drift, orientation, frame rate(24/29.97/30/59.94/VFR), audio(44.1k/48k, mono/stereo), codec, color(SDR/HDR), 취소 후 찌꺼기 없음, overwrite 정책, disk full atomic failure. 같은 프로젝트를 여러 번 export해 decoded output 수준에서 동일성 검사(비트스트림 byte equality는 부적절).

### P0/P1 — 실기기와 TCC를 별도 Gate로 분리

"실기기 2종"과 "TCC 권한 2건"은 Beta Release Gate. 권한은 Not Determined→Allow/Deny, Allow→revoke, Deny→Settings 안내→복구 흐름까지.

### P1 — 테스트 수보다 Risk Coverage

1,480 tests는 좋지만 이제 테스트 개수 자체보다 release-risk coverage(Critical Capability별 관리: Persistence·Migration·Crash recovery·Permissions·Real device·Distribution이 상대적 약점). 대표 시나리오 4종×2회보다 시나리오 직교성이 중요.

### P1 — 장시간 편집 성능

30분 타임라인 인덱스 p95는 index 성능 증거일 뿐 Timeline UX 성능이 아님. 30분/1시간/2시간 프로젝트, 수백~수천 clip, rapid scrub, thumbnail/waveform 생성, split 반복, multi-select, undo/redo 반복, zoom, export 경합, 메모리 high-water mark, 30~60분 soak에서 메모리 증가 측정.

### P1 — App Store / TestFlight 준비

Apple은 개인정보 처리방침 URL과 Required Reason API의 privacy manifest 사유 선언을 요구. TestFlight 내부 테스트 그룹, 외부 테스트용 Beta App Description·Feedback Email 필요. 체크리스트: PrivacyInfo.xcprivacy validation, Privacy Policy URL, Usage Description, Entitlements audit, Beta App Description, Feedback Email, Known Issues, Release Notes, Crash symbolication, Diagnostic export.

## 2. 백로그가 소진된 동안 루프가 자율적으로 할 일

기존 규칙(신규 백로그 없으면 개발 안 함)을 없애지 말고 **Standing Autonomous Quality Backlog(QAUTO — Autonomous Quality & Verification Lane)**를 만들 것. 제품 기능을 변경하지 않는 작업만 사전 승인:

- A. Measurement Harness Qualification(최우선): 모든 기존 벤치마크에 positive/negative control·zero detector·threshold 사전등록·dataset hash·harness version 검사
- B. Project Format Fuzz / Property Test: add/split/move/trim/role change/delete/undo/redo/save/reload 무작위 생성 + invariant(duration≥0, ID unique, references valid, undo→prev, redo→same, save/reload→semantic equality)
- C. Fault Injection 확대: disk full, permission denied, read-only destination, source deleted/disconnected, temp dir failure, export/task cancellation, corrupted project, partial write — 특히 project save 중 ENOSPC
- D. Media Compatibility Corpus: H264/HEVC/portrait/VFR/4K/60fps/silent/mono/48k/very short/odd resolution/HDR — 성공 또는 명시적 unsupported 둘 중 하나
- E. Concurrency/Interaction Torture Test: scrub→split→undo→play→seek→export→cancel→redo→save seed 기반 생성, 실패 seed는 regression fixture
- F. Static Release Audit: TODO/FIXME 증가, force unwrap, fatalError, debug endpoint/menu, dev entitlement, localization key mismatch, missing resource, privacy manifest, usage description 누락, sandbox 차이, release 빌드 debug 코드, feature flag 기본값
- G. Evidence 재현성: evidence YAML(app_commit/harness_commit/dataset_sha256/env/threshold/observed/result) 정규화, SHA 변경 시 PASS→STALE 자동 전환

**자율 루프가 하면 안 되는 것**: CA-18 알고리즘 임의 개선, 새 사용자 기능, UI/UX 구조 변경, schema version 증가, entitlement 변경, TCC 정책 변경, telemetry 신규 도입, third-party dependency 추가, codec 지원 확대, threshold 사후 변경, 가격/상품 정책 구현.

"검증을 깊게 하는 것은 자율 허용, 제품 의미를 바꾸는 것은 백로그 승인을 요구" 구조.

## 3. 베타 관점 우선순위 재조정

Feature→Measurement→Beta 순서에서 Release path→Data integrity→Core workflow correctness→Real-device reliability→Beta operability→Differentiating features 순서로.

| 우선순위 | 영역 | 판단 |
|---|---|---|
| P0-1 | iOS CI → Archive → Signing → TestFlight → Device | 베타 경로 자체 |
| P0-2 | Project v1~v9 migration / save / recovery | 사용자 데이터 보호 |
| P0-3 | Import → Edit → Save → Reopen → Export E2E | 최소 신뢰성 |
| P0-4 | 실기기 2종 + TCC allow/deny/revoke | 실제 환경 |
| P0-5 | Export correctness + failure atomicity | 결과물 신뢰성 |
| P1-1 | Crash/symbolication/Diagnostic/Feedback | 베타 운영 능력 |
| P1-2 | Privacy/entitlement/App Store Connect readiness | 배포 준비 |
| P1-3 | Codec/format compatibility matrix | 실제 사용자 파일 |
| P1-4 | Long timeline soak/performance/memory | 편집기 품질 |
| P2 | Onboarding 개선 | 진입 경험 |
| P2 | CA-20 Role UX polish / CA-21 확대 검증 | 차별화 |
| P3 | CA-18 speaker diarization | 현재 FAIL이므로 베타 제외 |

CA-18은 당분간 내려놓는 게 맞음(목표 ≤10% vs 실측 31.9~40.1% — 단순 tuning gap 아님). 실인간 녹음 도착 전까지 Feature flag OFF·UI hidden·Known limitation·Harness 유지. 상용화 일정과 결합 금지.

**Beta Readiness Gate(신규 제안)**: G1 Build Integrity / G2 Project Integrity / G3 Media Integrity / G4 Device Integrity / G5 Operational Readiness / G6 Beta UX — G1~G5 중 하나라도 FAIL/BLOCKED → External Beta NOT READY. G6 실패 → Internal Beta 가능.

**macOS/iOS 베타 분리 검토**: iOS는 환경/계정/실기기 의존성이 크므로 별도 release train 권장. 단 Mac↔iOS 프로젝트 호환이 핵심 기능이면 묶을 것.

## 결론

1순위 Measurement Qualification Gate, 2순위 Project Integrity/Migration Gate, 3순위 CI→Signing→TestFlight→Real Device 배포 증거 체인. 그 다음 Export correctness와 미디어 호환성. 대기 중 자동화 루프에는 QAUTO lane(fuzz/property, fault injection, media corpus, soak, evidence 재현성)까지만 자율 허용. 이 구조면 "계속 기능을 만드는 Agent"에서 "출시 가능한 상태를 증명하고 약한 증거를 찾아내는 Release Engineering Agent"로 진화.
