이번 2회차에서 가장 중요한 성과는 결함 3건 자체보다, 세 건이 모두 **"측정 실패·미실행·빈 결과가 정상 PASS처럼 해석될 수 있는 Oracle fail-open 계열"**이라는 공통점을 확인했다는 점입니다. 그래서 아래 3가지 리뷰도 이 관점에서 보는 게 좋습니다.

## 1. 이번 증분에서 놓쳤거나 과소평가한 부분

첫째, 3건을 개별 버그로만 닫으면 안 됩니다. CA-18의 0 detected → 0% confusion, CA-12의 self-test 존재하지만 미호출, CA-04의 ffprobe 실패 → "" == ""은 모두 같은 실패 클래스입니다.

즉 앞으로는 결과를 단순 PASS/FAIL 두 상태로 두기보다 최소한 아래처럼 나누는 것이 좋습니다.

- PASS: 측정이 정상적으로 성립했고 임계값 충족
- FAIL: 측정은 정상적으로 성립했지만 임계값 미충족
- INVALID: 데이터 없음, degenerate input, 판독 불가, 전제조건 불충족
- ERROR: 하니스·외부 도구·실행 자체 실패

그리고 release gate에서는 PASS만 통과, 나머지는 전부 차단해야 합니다.

특히 다음을 공통 금지 규칙으로 두는 것이 좋습니다.

- null → 0
- [] → 0%
- "" == "" → true
- NaN → default value
- exit code != 0 → empty output
- test not executed → assumed success

둘째, "self-test가 존재한다"와 "실제 판정 경로에서 실행된다"를 분리해서 봐야 합니다. CA-12가 이 점을 정확히 보여줍니다. 따라서 QAUTO-01 감사 축에 사실상 하나를 더 추가하는 게 좋습니다.

**Control/Gate Reachability** — 실제 실행 경로가 다음처럼 연결되는지 확인해야 합니다.
driver → preflight → positive/negative/invalid controls → real measurement → metric → threshold → gate
테스트 함수가 저장소에 존재하는 것만으로는 부족합니다.

셋째, 현재 evidence binding 1/8, harness pin 1/8이면 기존 실측값을 전부 폐기할 필요는 없지만, release evidence로는 아직 미자격으로 보는 게 맞습니다. 즉 QAUTO-01의 진짜 완료 조건은: 공통 하니스 규약 완료 + 8개 하니스 전부 새 규약으로 재실행 + 모든 결과 provenance-qualified,까지가 되어야 합니다.

넷째, harness SHA만 고정해서도 부족합니다. MovieCut 측정은 ffmpeg/ffprobe, OS, 모델, codec, AVFoundation 같은 외부 실행 환경에 영향을 받을 수 있으므로 최소한 결과 manifest에 다음 정도는 남기는 것이 좋습니다: source commit SHA · harness SHA · dataset/input SHA · threshold/config SHA · external tool version · model/weight SHA(해당 시) · OS/architecture · raw evidence SHA · derived metric · final result.

다섯째, 보고서의 "제품 소스 무변경"은 제품 regression 측면에서는 긍정적이지만 release 위험이 낮다는 뜻은 아닙니다. 하니스와 gate는 control plane입니다. 제품 코드가 그대로여도 gate가 잘못되면 불량 빌드가 베타로 통과할 수 있습니다. 따라서 **gate 코드 변경도 release-critical code로 취급**하는 것이 좋습니다.

## 2. QAUTO-01 잔여 축 우선순위

거짓 판정 리스크만 기준으로: **1순위 음성(negative) control 4종** — 단순 fixture 추가가 아니라 "하니스 시작 → control preflight 자동 실행 → 하나라도 예상과 다름 → 실제 측정 실행 금지 → gate ERROR/INVALID" 형태. 각 하니스에 known-good·known-bad·**known-invalid/degenerate** 최소 3종(이번 CA-18·CA-04는 "측정 자체가 성립하지 않는 상황"에서 터졌으므로 known-invalid가 핵심). **2순위 harness pin + evidence binding**(한 증분으로 묶을 것 — result가 source SHA/harness SHA/threshold SHA/raw evidence SHA/outcome을 가리켜야). **3순위 dataset SHA pin**(현재 발견된 결함 클래스는 dataset drift보다 Oracle false PASS). QAUTO-01을 CLOSED로 선언하기 전에는 세 가지 모두 끝나야 합니다.

## 3. 매일 1증분 속도일 때 베타 일정 관점 순서

번호 순서(01→02→03→04→06)는 권하지 않습니다. 핵심은 QAUTO-06 soak가 wall-clock 시간이 필요하다는 점 — 늦게 시작하면 코드 작업이 끝나도 베타가 늦어집니다.

추천 순서: QAUTO-01 완결 → **QAUTO-06 soak 시작(닫는 건 나중·시작은 빨리)** → QAUTO-02 프로젝트 무결성 → QAUTO-03 출력 무결성 → QAUTO-04 베타 게이트 문서(앞선 결과를 고정된 release contract로 전환 — 여기서부터 threshold freeze: 변경 시 새 gate version+재검증) → QAUTO-06 최종 회수. QAUTO-05는 사용자 대기 의존이라 병렬 관리.

**베타 일정에서 QAUTO 외에 가장 먼저 결정할 것**: macOS/iOS beta release train 분리 여부(가격·스크린샷보다 먼저 — CI matrix·signing·베타 그룹·RC SHA·증거·회귀 범위·롤백 단위에 직결). 그리고 verify_gate 4/5의 iOS 환경 블록은 개발 중엔 허용되지만 beta candidate 시점엔 예외 불가 — 최종 베타 게이트는 candidate commit SHA = CI 검증 SHA = 배포 artifact SHA여야 하며, "push 시 CI가 커버한다"가 아니라 해당 RC SHA의 PASS evidence가 실제로 존재해야 합니다.
