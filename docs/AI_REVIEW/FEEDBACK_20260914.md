## 1. 컨트롤 preflight 설계: 적절함. 다만 "known-invalid 1개"만으로 끝내지는 않는 게 좋음

제안한 구조(known-invalid control → gate 발화 확인 → 성공해야 실제 측정 → control 결과도 qauto 증거로 저장)는 맞습니다. 특히 control 실패 시 실측 자체를 금지하는 것이 핵심입니다 — 단순 경고 후 계속 실행하면 Oracle fail-open 방어가 되지 않습니다.

추가로 잠글 부분 4가지:

1. control은 단순히 PASS가 아니면 성공이 아니라 **예상 상태와 정확히 일치**해야 합니다(malformed input 기대 INVALID인데 FAIL도 성공으로 보면 안 됨).
2. 기대와 다른 control 결과는 제품 FAIL이 아니라 **automation/control 자체의 ERROR로 취급**(expected INVALID / observed PASS → ERROR: CONTROL_BREACH, 이후 measurement 0건).
3. control은 반드시 실제 measurement와 **같은 gate implementation / same code path**(별도 mock validator 우회 금지).
4. QAUTO-01 CLOSED 전에는 **positive control도 1개**(negative만 있으면 "항상 reject하는 고장난 gate"가 정상으로 보임).

최종 형태: environment sanity → negative control(expected INVALID/FAIL) → positive smoke control(expected PASS) → real measurement. 이번 회차는 negative preflight만으로도 타당하나, CLOSED 조건에는 positive smoke까지 권함.

qauto 기록에는 최소한 다음 관계가 필요하며, **control PASS가 로그상 참고사항이 아니라 measurement 실행 권한을 발급하는 조건**이어야 합니다(fail-open 구조적 차단):

```json
{
  "phase": "control_preflight",
  "control_id": "ca18-known-invalid-v1",
  "expected_verdict": "INVALID",
  "observed_verdict": "INVALID",
  "measurement_authorized": true,
  "gate_sha256": "...",
  "harness_sha256": "...",
  "run_id": "..."
}
```

실패 시: `expected INVALID / observed PASS → verdict ERROR, reason CONTROL_BREACH, measurement_authorized false`.

## 2. provenance manifest: qauto-*.json 확장보다 별도 run-level manifest 권장

단 하나를 덮어쓰는 방식이 아니라 **실행(run)별 immutable manifest**:

```
.build-check/history/
  run-20260914T041500Z/
    provenance.json      (run_id·app commit·gate/driver/harness SHA 목록·dataset SHA 목록·toolchain·CI/RC/artifact SHA·환경·시각)
    qauto-ca18.json      (run_id·개별 결과·observed·verdict·control 결과·manifest_sha256·dataset_sha256)
    qauto-ca21.json
```

원칙: **Run Manifest = 실행 환경과 입력의 원장 / qauto JSON = 개별 측정과 판정의 증거**. 전부 복제하면 필드 하나가 우연히 달라지는 provenance drift가 생김. manifest 자체도 SHA를 계산해 각 qauto 결과가 참조(`manifest_sha256`)하면 provenance 변경 자체도 검출 가능. QAUTO-05의 RC SHA=CI SHA=artifact SHA 검증도 이 manifest에 포함이 자연스러움.

## 3. 디스크 guard: 무인 루프라면 필수에 가깝다

판단 기준은 "다음 작업을 안전하게 실행할 headroom이 있는가"뿐. 3단계 권장:

| 조건 | 동작 |
|---|---|
| free <25Gi 또는 직전 대비 −10Gi 이상 | WARN, 계속 실행 |
| free <15Gi | 새 build/test/soak 시작 금지 |
| free <8~10Gi | HARD STOP |

특히 soak 전 <15Gi block 필수(Xcode·derived data·AVFoundation 산출물이 순간적으로 크게 쓰므로, 디스크 부족 실패가 제품/테스트 실패와 섞이는 것을 방지). 기록 예: `{"disk_free_gib": 13.8, "disk_guard": "BLOCK", "reason": "INSUFFICIENT_DISK_HEADROOM", "increment_allowed": false}` — "왜 soak가 실행 안 됐는가"가 자동 설명됨. 자동 cleanup은 매우 보수적으로: 허용은 `.build-check/tmp`·automation-owned temp·식별 가능한 오래된 loop artifact뿐, 금지는 사용자 폴더·DerivedData 전체·Simulator 전체 삭제·출처 불명 파일. **disk guard는 aggressive cleanup 기능이 아니라 작업 중단 기능으로 설계**.
