## 1. BLOCK 적용 판정: 적절함

raw available 14.62 GiB < 15 GiB라면 이미 BLOCK 상태이므로, 새 swift test를 시작하지 않은 것이 맞습니다. 여기서 중요한 건 **가드 코드 구현 여부와 정책 효력은 별개**라는 점입니다. 이미 3회차에서 <15GiB = BLOCK을 채택했다면, QAUTO-07이 아직 드라이버에 완전히 연결되지 않았더라도 그 임계값은 즉시 운영 규칙으로 효력이 있습니다.

그래서 이번처럼 QAUTO-01 스키마 확장을 실제 구현·검증까지 밀어붙이지 않고, 등록만 한 뒤 검증 가능한 완결 증분을 연기한 것도 좋습니다. 오히려 BLOCK 상태에서 코드를 수정하고 검증하지 못한 채 남기는 것이 더 나쁩니다.

다만 앞으로는 BLOCK 해제 조건에 **hysteresis**를 하나 두는 것을 권합니다. 예를 들어 <15GiB에서 BLOCK 진입, 다시 **>=20GiB**가 되어야 build/test 재개 허용 — 15GiB 경계에서 진입·해제를 반복하는 현상을 막을 수 있습니다.

## 2. DerivedData 2.9G: 전체 삭제 금지 유지, 프로젝트 귀속 캐시만 선별 삭제 허용

전체 DerivedData 삭제 금지는 유지하는 것이 맞습니다(다른 프로젝트와 Xcode 전역 상태까지 건드릴 수 있음). 대신 MovieCut 루프가 만든 것으로 귀속성을 증명할 수 있고 재생성 가능한 캐시는 QAUTO-07의 ephemeral cache 화이트리스트에 포함해도 됩니다.

삭제 기준 5가지: ①현재 MovieCut 프로젝트/workspace에서 생성된 것임이 명확할 것 ②source·fixture·signing이 아니라 재생성 가능한 build/index 산출물일 것 ③현재 xcodebuild·swift·Xcode Build Service가 사용 중이지 않을 것 ④오래된 캐시부터 삭제할 것 ⑤목표 free space 확보에 필요한 만큼만 삭제할 것.

"개별 scheme 캐시"보다 **프로젝트 귀속성과 내부 산출물 종류 기준**이 더 안전(Xcode DerivedData는 scheme 기준으로 깔끔히 분리되지 않음). 정책 문구: **"DerivedData 전체 삭제 금지. 현재 저장소가 생성했다고 귀속 증명 가능한 재생성 가능 캐시에 한해 oldest-first, required-space-only 방식으로 삭제 허용."**

## 3. BLOCK 구간: 완전 정지 아님 — 읽기 전용+공간 회수 작업만 허용

BLOCK과 STOP은 역할 분리: <15GiB BLOCK은 "새 build/test/benchmark 금지"이지 "모든 작업 정지"가 아님. df·du·manifest 확인·qauto 레코드 조회·git 상태 점검 같은 read-only 진단은 허용.

단, "아카이브·압축"은 주의 — 같은 볼륨에 tar.gz를 새로 만들면 일시적으로 디스크를 더 소비하므로 BLOCK 복구 작업으로 부적절. BLOCK에서는 **실제로 free space를 늘리는 작업만**: retention에 따른 오래된 qauto 레코드 삭제·MovieCut 귀속 ephemeral cache 삭제·다른 볼륨 이동·기존 압축본으로 원본 대체. 같은 디스크 "압축 생성→원본 삭제"는 기본 금지.

운영 규칙 한 줄: **WARN <25GiB 정상 실행 가능하되 신규 대형 작업 자제 / BLOCK <15GiB build·test·benchmark 금지, read-only 진단과 화이트리스트된 공간 회수만 / STOP <10GiB 개발 작업 완전 정지, 공간 확보와 상태 확인만.**
