## 1. 스키마 확장 설계 — 4회차 요건 충족

ABORT_BEFORE_VERDICT + verdict_present=false로 "판정 미발급"과 "파서/기록 누락"을 분리했고, run_id로 동일 실행의 3개 컨트롤 레그와 실측을 묶어 stale 재사용을 막았으며, measurement_authorized와 ERROR_CONTROL_BREACH로 control PASS가 실제 실행 권한의 선행조건이 되도록 했습니다.

다만 QAUTO-01을 CLOSED로 승격하기 전 **마지막 확인 3개**를 권합니다:
1. 이전 실행의 PASS 레코드가 남아 있어도 run_id가 다르면 현재 measurement가 절대 실행되지 않는 stale-injection 테스트
2. control mismatch 시 measurement_authorized=false뿐 아니라 실제 scorer/measurement invocation 자체가 발생하지 않는지 확인
3. ERROR_CONTROL_BREACH 경로가 최종 프로세스 성공(rc=0)으로 끝나지 않는지 확인

이 세 가지까지 통과하면 **QAUTO-01은 더 이상 CONDITIONAL로 둘 이유가 없습니다. CLOSED가 맞습니다.**

## 2. QAUTO-01 이후 우선순위 — 증거 체계 고정이 재기준화보다 먼저

권장 순서: **run-level immutable manifest → dataset SHA pin → CA-18 scorer contract → 8-harness rebaseline.**

이유: 재기준화를 먼저 돌리면 baseline 숫자는 생기지만, 나중에 "그 숫자가 어떤 scorer/version/dataset/git 상태에서 나왔는가"를 다시 보강해야 함. manifest와 SHA pin을 먼저 만들면 이후 재기준화 결과가 처음부터 재현 가능한 증거가 됨.

run-level manifest 최소 필드: run_id, git_sha, harness_version, scorer_version, fixture/dataset SHA, control verdicts, measurement_authorized, 시작시각.

CA-18 scorer contract는 그 다음 — 25ms 미달 무음 같은 degeneracy 케이스는 "점수가 얼마냐"보다 **어떤 입력을 valid/invalid로 간주하고 어떤 결과를 의미 있는 측정값으로 인정하는가**를 contract로 못 박는 것이 중요.

**8하니스 재기준화는 현재 21.67GiB WARN에서는 미루는 게 맞음.** 구분: ≥20GiB=hysteresis 해제(중단 상태에서 작업 재개 가능) / ≥25GiB=정상적인 비용성 테스트가 비교적 안전한 영역 / 그 이상=장시간·대량 작업. **20GiB는 "heavy workload safe line"이 아니다.** 어제 14.6GiB까지 내려간 실측 변동성을 보면 21.67GiB에서 8하니스 일괄 재기준화는 감수할 필요 없는 리스크.

## 3. WARN 구간의 soak — passive만 지금, active는 GREEN에서

wall-clock을 벌자는 판단은 맞으나 soak를 둘로 나눌 것:
- **Passive soak(지금 시작 가능)**: 프로세스 생존·메모리 증가 추세·temp/cache 증가량·disk_guard 상태 변화·crash/hang 여부·기존 artifact를 이용한 경량 health probe — 빌드나 대량 fixture 생성 없이 장시간 안정성 데이터 축적.
- **Active soak(반복 render/export/import·pipeline 재실행·대량 로그/캐시 생성)**: 지금은 이르다. GREEN(≥25GiB) 진입 후.

추가로 QAUTO-06에는 disk_guard를 시작 시 1회 preflight로만 쓰지 말고 **runtime watchdog**으로: GREEN/WARN=계속 / BLOCK=신규 iteration 중단·현재 증거 flush 후 graceful abort / STOP=즉시 종료. soak 시작이 25GiB였어도 실행 중 급감 시 정책 위반이 되지 않도록.
