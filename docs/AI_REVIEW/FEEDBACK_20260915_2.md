## 1. 매니페스트 설계 — 현재 구조로 충족. 추가 권고

exit trap에서 모든 종료 경로를 잡고, WORK 소거 전에 해당 run_id 레코드와 fixture/dataset SHA를 취합한 뒤 write-once로 남기는 방식은 6회차 필드 집합을 충족합니다. 특히 정상 PASS뿐 아니라 ERROR_CONTROL_BREACH·measurement 미인가·중도 abort까지 동일 run provenance 안에 남을 수 있다는 점이 좋습니다.

추가 권고 4필드: **manifest_schema_version, finished_at 또는 duration_ms, driver_exit_code, worktree_dirty** — app_commit만 기록하면서 dirty working tree를 허용하면 실제 실행 코드가 commit과 다를 수 있음.

"파일이 이미 있으면 skip"은 immutable의 최소 구현일 뿐. 더 강한 계약: 기존 파일 존재 시 새 payload의 canonical hash 비교 → 같으면 정상 재호출, 다르면 **ERROR_PROVENANCE_COLLISION으로 non-zero exit**. accidental overwrite뿐 아니라 동일 run_id 재사용·내용 충돌까지 잡음.

필드 추가 권고: record_count, manifest_sha256(포렌식). 반대로 OS 패키지 전체·환경변수 전체 덤프는 과함 — 목표는 "이 측정이 어떤 코드·드라이버·도구·입력·컨트롤 상태에서 수행됐는지 재구성 가능" 수준이면 충분.

## 2. dataset SHA pin — 기록과 pin은 다르다. 실행 계약이어야

단순히 현재 SHA를 manifest에 기록하는 것은 사후 증거고, pin은 불일치하면 measurement 자체를 시작하지 못하게 하는 실행 계약. 권장 흐름: **baseline 존재 확인 → 실제 dataset SHA 계산 → 기준 SHA 비교 → MATCH일 때만 measurement_authorized=true → 이후 control/measurement 진행.**

기준값은 shell 하드코딩 대신 버전 관리 파일(예: `qa/baselines/dataset-lock.json`). 상태는 boolean보다 **MATCH / MISMATCH / BASELINE_MISSING / HASH_ERROR** 4종. dataset이 디렉터리면 **tree hash 방식**(상대경로 정렬 후 relative_path+file_sha256 집합을 canonical hash — tar 자체 해시는 metadata·순서 영향)으로 플랫폼·mtime 차이 오검출 방지.

mismatch 시 WARN이 아니라 measurement 거부: `dataset_pin_status=MISMATCH · measurement_authorized=false · ERROR_DATASET_PIN_MISMATCH · exit 1`. manifest에는 expected/observed SHA 둘 다 기록.

## 3. passive soak — 다음 증분으로 승격 승인

manifest가 생겨서 soak 결과를 단순 heartbeat가 아니라 "어떤 provenance를 가진 run을 관찰했는지"와 연결할 수 있게 됨. 다만 디스크 19.75GiB 하향 추세이므로 다음 증분은 **passive-only** — active soak(measurement 반복)은 아직.

passive soak v1 = 새 빌드·대형 fixture 재생성 없이 최근 manifest만 읽어 확인: manifest freshness, JSON parse 가능, schema completeness, 동일 run_id 일관성, control 3-leg 상태, measurement_authorized, driver exit, disk guard 상태, watchdog heartbeat, stale/orphan WORK 존재 여부.

soak 결과는 manifest와 분리: `.build-check/history/runs/`(immutable execution evidence) vs `.build-check/history/soak/`(append-only observation). 판정은 **HEALTHY / DEGRADED / STALE / INVALID_PROVENANCE** — 최근 manifest가 오래됐는데 마지막 상태가 PASS라는 이유로 HEALTHY 유지 금지, freshness는 독립 조건.

## 우선순위·최종 결론

**passive soak v1 → dataset SHA pin preflight → manifest collision/self-hash hardening → 디스크 GREEN 복귀 후 active soak.** 최종: ① manifest 설계 승인(단 collision detection·dirty-state 보강 권고) ② dataset pin은 commit-managed baseline+preflight strict compare ③ passive soak NEXT 승격, active는 GREEN 이후.
