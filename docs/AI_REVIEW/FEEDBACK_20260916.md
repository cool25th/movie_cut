## 1. BLOCK 중 passive soak 실행 — 승인

BLOCK의 목적은 디스크를 더 소비할 수 있는 새 build/test/fixture 생성을 막는 것이지 상태 관찰 중단이 아님. 이번 passive soak은 새 build 없음·test 없음·fixture 변경 없음·기존 manifest/guard 상태 읽기 중심이므로 BLOCK-safe. 오히려 BLOCK일 때 soak까지 멈추면 "왜 새 run이 없는가"·provenance freshness·orphan WORK를 관찰할 수 없어짐.

다만 "read-only"라는 용어는 부정확 — soak/에 append하기 때문. 명확한 정의: **BLOCK_SAFE observer = no build + no test + no fixture mutation + no WORK creation + bounded append-only evidence write.** 이번 실행은 BLOCK 규칙 위반 아님 / GO.

## 2. guard BLOCK/STOP → DEGRADED 매핑 — 유지 (단순 참조 필드는 비추천)

soak의 verdict가 "다음 run을 수행할 수 있는가"까지 나타내는 health라면, manifest가 valid+fresh여도 disk_guard=BLOCK을 HEALTHY라 부르면 운영 의미가 틀림. 4상태 의미 고정:

- HEALTHY: provenance 정상 + fresh + 실행 방해 환경 없음
- DEGRADED: provenance는 신뢰 가능하지만 실행 환경이 저하됨
- STALE: provenance는 유효하지만 freshness 초과
- INVALID_PROVENANCE: evidence 자체를 신뢰할 수 없음

따라서 예상값 **DEGRADED(reason=DISK_GUARD_BLOCK)가 정확**. 단, BLOCK과 STOP을 한 단어로 평탄화 금지 — **reasons는 다중 보존**(verdict=DEGRADED·reasons=[DISK_GUARD_BLOCK] / STOP이면 [DISK_GUARD_STOP]). freshness와 resource가 동시에 나빠질 수 있으므로, 48h 경과로 STALE로 올라가도 DISK_GUARD_BLOCK reason은 남겨야 함. precedence: INVALID_PROVENANCE > STALE > DEGRADED > HEALTHY.

## 3. 반복 디스크 급락 — REPORT+soak만으로 부족. STOP 하향보다 escalation 규칙

관측 패턴: 41→26→25→14.6 BLOCK→21.7 회복→19.7→13.49 BLOCK — 단발성 부족이 아니라 **회복 후 재발하는 instability**. ≥20GiB 한 번 찍었다고 BLOCK 해제했는데 곧 13GiB대로 떨어짐 — 현재 hysteresis는 **capacity recovery는 확인하지만 stability recovery는 확인하지 못함**.

**RECURRENT_BLOCK 상태 추가**: rolling 24~36h 내 BLOCK 2회 이상 → build/test 계속 금지·passive soak만 허용·자동 cleanup/rebaseline 금지·보고서에 operator_action_required 표시·20GiB 이상 회복돼도 즉시 WARN 복귀 금지.

**BLOCK 해제 강화 — 권장안 A(가장 단순·안전): ≥20GiB가 2회 연속 관측되어야 해제.** (안 B: ≥20GiB AND Δ≥−2GiB는 더 민감하지만 튜닝 불필요한 A 권장.) STOP(<10GiB)은 절대 위험 구간으로 유지. 자동 cleanup 강화는 여전히 비추천 — 소비가 MovieCut 귀속이라는 증거가 없으므로 자동화가 사용자 파일·타 앱 데이터를 건드리는 방향이 훨씬 위험.
