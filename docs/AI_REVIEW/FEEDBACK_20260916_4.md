## 1. ca04_* 5종 pin 1차 대상 — GO

Git tracked/committed binary이고·드라이버의 실제 입력이고·단순 샘플이 아니라 oracle 결과를 만드는 입력 데이터(VFR/10-bit/BT.2020 PQ/rotation — 바이트 변경이 테스트 의미 자체를 바꿈)이므로 "코드는 그대로인데 데이터만 바뀌어 PASS/FAIL 의미가 달라지는" provenance 위험의 우선 대상이 맞음.

성격 구분: known-answer/frame-count oracle fixture는 **적극 pin** 대상(fixture 변경은 사실상 테스트 코드 변경). known-invalid control은 "invalid라는 이름"이 아니라 "그 특정 invalid 바이트 시퀀스가 control 실패 조건을 정의하는가"로 판단 — CA-18/21 같은 control fixture가 있다면 같은 원칙으로 lock 편입.

## 2. lock schema — 현재 필드로 gate 충분. fixture_id 추가 권장

path(artifact locator)·sha256(authoritative identity)·size(보조 sanity)·updated_by_commit(변경 근거)로 P0 gate 역할은 수행. 장기적으로 **fixture_id**(논리적 identity — 경로를 identity로 쓰면 rename/move가 dataset identity 변경으로 해석됨)와 **oracle_role/purpose**(mtime보다 가치) 추가 권장. **mtime은 lock에 넣지 말 것**(checkout·copy·restore·archive 해제만으로 변동 — provenance identity 부적절). 지금 당장 fixture_id 없다고 1차를 막을 이유는 없음 — 완료 후 schema v1.1에서 추가.

## 3. --init 위험 — 선택은 명확히 (a). --force 제거

dataset pin의 목적은 "현재 파일이 정상인가"가 아니라 **"현재 파일이 이미 승인된 바이트와 동일한가"** 확인. --force가 있으면 fixture 오염 → --init --force → 오염된 SHA가 새 baseline → MATCH → 정상 데이터처럼 보이는 **관리자 우회구**가 됨. mtime+git dirty 기록만으론 불충분(dirty=true는 HEAD와 다르다는 사실만 말할 뿐 승인을 증명하지 못함).

**권장 init/update 계약**:
- 최초 생성: dataset-lock 없음 + --init → 허용. 단 최소 조건: fixture가 **git tracked AND index/HEAD와 일치**(해시 계산 성공) — worktree에서 변조된 파일을 bootstrap하지 않기 위함(DIRTY_FIXTURE면 거부).
- lock 존재: --init → **ERROR_LOCK_ALREADY_EXISTS. --force 없음.**
- fixture 변경이 필요하면 init이 아니라 **baseline update**(별도 절차 — update_dataset_pin.sh 또는 --update. **automation에서 사용 금지**·manual operator 전용·5요건: git tracked·변경 명시적 staged/committed·이유 기록·oracle 영향 확인·lock 함께 갱신 — fixture와 lock 변경이 같은 review 단위에).
- updated_by_commit 주의: fixture를 수정하고 미커밋 상태에서 lock 갱신하면 HEAD를 가리켜 애매 — "해당 fixture 바이트가 실제 존재하는 Git commit"을 가리킬 것. 장기적으로 **git_blob_sha** 병기 권장(SHA-256=파일 provenance, blob SHA=repository provenance — 2차 hardening).
