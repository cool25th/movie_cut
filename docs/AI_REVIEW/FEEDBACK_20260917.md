## 1. journal 대조 — path+new sha만으로는 부족. update_id 도입

최소 대조 키: fixture_id+path+old_sha256+new_sha256+old/new_git_blob_sha 묶음. 권장: **update_id = sha256(fixture_id+path+old_sha256+new_sha256+old_git_blob_sha+new_git_blob_sha+base_head_commit+reason)**를 update_history와 journal 양쪽에 동일하게 기록. verify 판정:

```
update_history 있음
 └─ 동일 update_id journal 검색
      ├─ 0건 → MISSING_UPDATE_JOURNAL
      ├─ 1건 → 상세 필드 대조 (일치 PASS / 불일치 UPDATE_JOURNAL_MISMATCH)
      └─ 2건 이상 → DUPLICATE_UPDATE_JOURNAL
```

journal의 실질 가치는 절대 변조 불가가 아니라 **lock 단독 변경·journal 단독 삭제·기록 누락을 서로 다른 두 기록의 교차 검증으로 탐지**하는 것. 공격자가 lock+journal+Git history를 모두 재작성하면 막을 수 없음 — 보안 경계 표현: **update journal = immutable ledger가 아니라 Git history에 같이 들어가는 independent provenance witness**. hash-chain(prev_event_hash)은 중간 삭제·순서 변경 탐지에 유용하지만 전체 재생성은 못 막으므로 후순위.

## 2. journal은 Git에 커밋 권장 + provenance unit

Git에 넣지 않으면 새 clone·checkout·디스크 정리만으로 journal이 사라지고 fail-closed 때문에 과거 baseline이 갑자기 검증 불가능해짐. 최상 계약: **fixture 변경 → --update → lock 변경+journal append → 동일 commit**으로 3개가 하나의 provenance unit으로 이동. 이렇게 하면 checkout 간 동기화는 문제가 아니라 장점(과거 commit checkout 시 그 시점 fixture와 provenance가 같이 복원).

명칭 정확화: journal의 **head_commit → base_head_commit**(update 직전 HEAD — 새 fixture를 포함한 commit은 아직 존재하지 않을 수 있음; result_commit은 순환 문제로 넣지 않음). JSONL merge conflict는 1인+단일 자동화에선 걱정 불필요 — 빈번해지면 event-per-file(update-events/<update_id>.json)로.

## 3. 오래된 lock의 journal 유실 복구 — 일반 --update와 완전 분리

자동 복구(verify 실패 → 현재 lock으로 journal 자동 생성 → PASS)를 허용하면 조작된 lock도 사후 정상 포장 가능 — 금지. 명시적 수동 명령: `--repair-missing-journal --fixture-id --reason` — **Git history에서 해당 update를 독립 증명할 수 있을 때만** 허용(parent commit fixture SHA=A → update commit SHA=B·lock history A→B 존재 → Git이 증명). 복구 이벤트는 정상 update로 위장 금지: kind=recovered_missing_update_journal·recovered_at=현재(과거 시각 복원 금지)·evidence(base/change commit). Git으로도 증명 불가 시 억지 제거 말고 **UNRECOVERABLE_UPDATE_PROVENANCE**로 상향 + 필요 시 `--rebaseline`(kind=provenance_reset·reason·현재 해시·operator acknowledgment·새 provenance chain 시작).
