23회차 repair contract 방향은 좋습니다. repair가 과거를 "복원"하는 게 아니라 Git에 남아 있는 사실로 누락된 audit event를 사후 기록하고, 증명 불가면 rebaseline로 별도 chain을 여는 구분이 핵심.

## 1. Git 증명 3조건 — 한 단계 부족. historical lock tree 검증 추가 권장

현재 조건은 일반적 유실 복구에 충분하나, fixture와 lock을 **함께 사후 조작한 Git history도 형식상 통과 가능**. 권장 추가: ①base_commit이 change_commit의 ancestor ②Git tree에서 직접 base:path=A·change:path=B 재계산 ③**같은 두 commit의 lock 파일도 Git tree에서 직접 읽어 base lock=A·change lock=B·identity(fixture_id/path/oracle_role) 불변 확인** ④HEAD가 change_commit의 descendant ⑤base→change 사이 fixture/lock 변경이 여러 번이면 단순 A→B로 축약하지 말고 실패 ⑥update_id는 전달값 불신·증거로 재계산 ⑦동일 update_id recovery 재실행은 idempotent reject/skip. 개념: "현재 lock이 A→B라고 말한다" → "**Git의 과과 두 tree가 fixture와 lock 모두 실제 A→B였음을 독립 증명**". 경계: force-push/rewrite 공격자에는 repo 내부 repair로 원본성 증명 불가 — protected remote·signed tag·CI attestation은 repo 밖 신뢰 앵커 문제(스크립트에서 해결하지 않음). **GO, 단 historical lock tree+ancestry 검증을 repair 필수조건으로 추가 권장.**

## 2. --rebaseline — fixture별 provenance_epoch가 가장 명확

lock entry에 `provenance_epoch` 추가. 정상 update는 epoch 유지(A→B→C), rebaseline은 reset event로 epoch 연결(epoch_before/after·previous_terminal_sha·new_root_sha·reason·acknowledged_by) — 과거 chain을 수정/절단하지 않음. **이후 모든 update journal에 epoch 포함 + update_id에 epoch 포함 권장**: update_id=hash(fixture_id, epoch, old_sha, new_sha, base_commit, change_commit) — reset 전후 우연히 같은 A→B가 동일 update로 오인되지 않음. rebaseline 정의: "provenance 결함 치료"가 아니라 "**continuity를 명시적으로 포기하고 새 root를 선언**"하는 명령. verify 판정도 CONTINUOUS / **RESET_CONTINUOUS**(오류 아님 — 현재 epoch 내 완전·과거 reset 존재) 구분 권장 — escape hatch가 흔적 지우지 않게.

## 3. manual-only 한계 — 맞음. soft prevention + hard auditability

repo 내부 스크립트의 "사람만 실행 가능" 완전 증명은 불가(환경변수·TTY·CI 검사 모두 우회 가능) — security boundary로 포장하지 말 것. friction(--reason·--acknowledge-provenance-reset)은 두되 신뢰의 핵심은 **journal 탐지 가능성**: recovered/reset 이벤트의 actor·timestamp·HEAD·base/change commit·reason·epoch·evidence가 항상 남고 CI/verify가 이를 정상 update로 흡수하지 않고 별도 노출. "automation이면 거부"보다 강한 계약: **"repair/reset이 발생했다면 이후 어떤 automation도 그것을 정상 update처럼 숨길 수 없다"** — repair_count·reset_count·마지막 reset commit/epoch을 manifest/audit summary에서 확인 가능하게.
