24회차 방향은 맞습니다. fixture뿐 아니라 lock도 같은 Git history에서 A→B였음을 검증하면서, repair가 "현재 상태로부터 추정"이 아니라 **과거 상태를 독립 재구성**하는 기능으로 바뀜.

## 1. base에 lock 없으면 repair 거부가 맞음

--repair-missing-journal은 "원래 존재했어야 할 journal을 Git 증거로 복원"하는 것 — base tree에 lock 자체가 없으면 계약의 이전 상태가 존재했다는 증거가 없음(fixture blob A만 있다고 승인 baseline이었다고 소급 불가). **UNRECOVERABLE → explicit rebaseline 유지**. rebaseline은 "repair의 대체 수단"이 아니라 새 provenance chain 시작임을 명확히(다음 증분 epoch과 연결). "lock 도입 이전 fixture 정식화"가 필요해져도 repair 예외가 아니라 별도 bootstrap/import-baseline 계약으로.

## 2. idempotent skip — exit 0 유지하되 3상태 명시 + 핵심 예외

exit 0 + skip은 재실행 가능성을 깨지 않아 적절하나 "성공/skip"보다 상태를 전면에: **REPAIR_CREATED / REPAIR_ALREADY_PRESENT / REPAIR_FAILED**(`mutation=false`·`reason=duplicate_update_id` 포함·manifest/audit에도 구조화). **핵심 예외: 같은 update_id가 존재하지만 recovery 내용/evidence digest가 다르면 절대 skip 금지 — same update_id + same canonical recovery → exit 0/ALREADY_PRESENT, same update_id + different recovery → hard fail/PROVENANCE_CONFLICT.** 이 한 줄이 idempotency를 provenance 은폐 수단으로 변질시키지 않는 핵심.

## 3. ②epoch·③audit은 다음 2회차에 각 1증분 — 순서 epoch → audit

epoch은 필드 추가가 아니라 provenance 의미론 변경(rebaseline=새 chain 시작 경계)·audit은 그 의미론을 관찰하게 만드는 read 계층 — 한 커밋에 묶으면 epoch 계산 오류와 audit 표시 오류를 분리하기 어려움. 25회차 epoch: rebaseline→epoch N+1·normal update→유지·repair→원래 epoch 유지·**epoch 경계 넘어 repair 금지**·journal/recovery/run evidence의 epoch 일관성·구 epoch artifact 오인 방지. 26회차 audit: update_id·epoch·base/change·A→B·repair CREATED/ALREADY_PRESENT·rebaseline 여부·evidence/result를 한눈에 역추적. **Team ID가 먼저 들어오면 주 트랙 release 우선 — 이 둘은 독립 보조 증분으로 보존.**

## 4. 24회차 추가 고정 1건

"base..change에서 fixture/lock을 건드린 커밋이 정확히 1개"는 **두 path의 union을 변경한 commit set이 정확히 1개**라는 의미로 테스트를 고정할 것 — fixture 1회+lock 1회가 서로 다른 커밋이면 최종 tree가 A→B로 맞아도 반드시 UNRECOVERABLE. 이 조건까지 들어가면 repair v2의 증명 경계는 상당히 단단함.
