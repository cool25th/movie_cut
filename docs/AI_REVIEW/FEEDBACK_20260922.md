## 1. generation_id canonicalization — 필수 수정: generator_id 포함+domain/version prefix

- 같은 commit 안에 여러 generator가 존재할 수 있으므로 source_commit만으로는 부족 — **generator_id(와 source commit에서 완전 파생되지 않는다면 version)를 hash에 포함**.
- raw concatenation보다 **versioned/domain-separated canonical form**:

```
generation_id = SHA256(
  "MOVIECUT_GENERATED_FIXTURE_V1\0"
  + fixture_id + "\0" + generator_id + "\0" + generator_version + "\0"
  + generator_source_commit + "\0" + generation_parameters_hash + "\0"
  + input_count + "\0" + input_sha256[0] + "\0" ...)
```

- **입력 grammar 계약 고정**: fixture_id/generator_id `[A-Za-z0-9._/-]+`·generator_version printable ASCII(NUL 금지)·source_commit canonical lowercase git SHA·sha256 lowercase hex[64] — separator ambiguity보다 **schema evolution collision** 방어가 중요.
- **input ordering 의미 명시**: "canonical ordering"이 아니라 **"MUST preserve generator-declared input order"** — 정렬하면 입력 A,B와 B,A가 동일 generation으로 뭉개짐.

## 2. inputs 구조 — parallel array 대신 ordered pair sequence 권장

`input_fixture_ids[]`+`input_sha256[]` 이중 배열은 길이·순서 정합을 별도 invariant로 떠맡아야 함. `inputs: [{fixture_id, sha256}, ...]` pair sequence로 전환 권장 — generation_id 해시 입력도 pair에서 파생(A\0aaa, B\0bbb). 스키마 10필드라는 숫자 자체는 중요하지 않음.

## 3. QAUTO-02/03/04 — 독립 재실행 불필요, 대신 정책 규칙화

- QAUTO-02: verify_gate가 HEAD에서 PASS인지 확인으로 충분 — "메인 세션을 못 믿어서 다시 검증"은 가치 없음.
- QAUTO-03: **dependency 기반 재실행**(export pipeline·codec/preset·export fixture·FFmpeg/AVFoundation 경로·threshold 계약 변경 또는 release candidate 시만) — 매 회차 2회 media export는 소음. **커밋 메시지의 수치(41,699B 등)는 evidence source가 아님** — 사람용 projection이고 실제 증거는 gate script+machine 결과.
- QAUTO-04: 재실행 개념 아님 — gate definition unchanged+G1~G6 상태 갱신만.
- **CLOSED_GATE_REVALIDATION_POLICY 규칙화 권장**: closed gate는 매 회차 재실행 금지. 재실행 조건 5종: ①covered source 변경 ②fixture/threshold 변경 ③dependency/toolchain 실질 변경 ④release boundary의 fresh evidence 요구 ⑤기존 증거 무효/판독 불가. 보고 문구: "QAUTO-02 CLOSED — covered sources unchanged" / "QAUTO-04 STATEFUL — G4/G5/G6 status refreshed".
- 초기엔 "테스트를 많이 돌리는 것", 이제는 **"증거가 언제 다시 필요해지는지를 정확히 판정"**이 가치.

## 4. GEN-06 상태 3값 + 상태별 운영 규칙

- boolean 대신 **DETERMINISTIC / NONDETERMINISTIC_GENERATION / UNVERIFIABLE_GENERATION**.
- UNVERIFIABLE = "결과가 달랐다"와 분리 — generator source commit 부재·input이 lock에 없음·generator binary 소실·실행 불가 등 **재현·검증 자체가 불가능한 경우**.
- **NONDETERMINISTIC → REBASELINE으로 덮지 않는다**(비결정성 정상화 금지): 원인 해결 후 **새 generation identity**(예: identity에 encoder_version 추가)로. UNVERIFIABLE은 운영자 --reason+epoch 증가로 조건부 REBASELINE 가능.
- **REGENERATE는 verification event — provenance mutation 아님**: deterministic confirmation 시 lock 재기록 금지(immutable journal에만 event)·G1→H2 관측 시 exit!=0+lock untouched. "그 순간 provenance 검증기가 provenance 변경기가 된다". **REGENERATE=증명, REBASELINE=승인된 기준 변경**(--reason·epoch+1·operator intent·previous generation retained).
- 이벤트 4종 mutation 의미표: GENERATE=신규/신규/유지·REGENERATE=동일/동일/유지·REBASELINE=변경 가능/변경 가능/+1·REPAIR=원래 의미 복구/원래 증거 복구/원칙적 유지.
- **REPAIR 허용 범위는 좁게**: lock/기록 유실을 Git+generator source+input hashes+output hash로 독립 재구성 가능한 경우만. "generator가 현재 다른 output을 만든다"는 repair 대상 아님(NONDETERMINISTIC이어야) — repair가 deterministic failure를 덮지 못하게.
