# ChatGPT 피드백 — 2026-09-27 (32회차·seed failure promotion E2E)

> 원문: chatgpt.com 대화(본문+"계속" 연속 — DOM 속성 변경으로 표준 셀렉터 실패→main 텍스트 직접 회수) — 구조만 정리.

seed-promotion 설계 자체는 맞지만, 0.29GiB BLOCK headroom에서는 실제 Core 실행을 강행하지 않는 편이 좋습니다. WARN 명목 상태보다 BLOCK까지 절대 여유가 기준입니다.

## 1. immutable regression asset = "저장소에 커밋된 독립 fixture"

- runtime generated JSON = **promotion candidate/evidence** / source-controlled JSON = **immutable regression asset**.
- 실제 결함 승격의 완결: random failure→candidate JSON 자동 생성→standalone reproduction 확인→최소화/검토→`Tests/Fixtures/RandomRegressions/QAUTO06-NNNN.json` 커밋→일반 regression suite가 seed runner 없이 직접 소비.
- fixture 최소 필드 유지(fixture_id·origin_seed·failing_step·command_sequence·expected_invariant·discovered_at_commit).
- **불변식: fixture → direct deterministic replay**(fixture→seed를 random runner에 재투입은 승격 아님).
- **합성 injector 사례는 영구 커밋 금지** — promotion machinery 자체가 작동함을 증명하는 것까지. 영구 커밋 대상은 fixture가 아니라 **promotion pipeline test·fixture schema·standalone replay loader·seed runner 재호출 금지 assertion**. 흐름: synthetic failure→temp candidate→standalone replay FAIL 확인→injector 제거→동일 candidate replay PASS→candidate 삭제.

## 2. 실제 failure는 자동 포착+검토 후 promotion 2단계

- `AUTO_CAPTURE→PROMOTION_CANDIDATE→deterministic replay 확인→REVIEW→PROMOTED_REGRESSION`. **자동 = 실패 당시 증거 보존**(seed·failing_step·command history·initial state·violated invariant·HEAD commit — 사람 개입 전 필수 저장). **저장소 영구 승격은 검토 단계** — random failure가 항상 새 제품 결함은 아님(동일 원인 기존 fixture·하니스 오류·invalid scenario·infra nondeterminism·최소화 가능).
- 상태 머신: **DISCOVERED→CAPTURED→REPLAY_CONFIRMED→CLASSIFIED→PROMOTED→CLOSED** — CAPTURED는 증거 보존(지워질 수 있음), PROMOTED가 처음 영구 asset.
- 러너는 working tree에 직접 쓰지 않기 — staging 경로(tmp/qauto/promotion-candidates/)에 쓰고 promotion 명령이 명시적으로 복사.
- **production promotion path와 동일한 코드, persist destination만 교체**(persist(tempDirectory) vs persist(repositoryFixtureDirectory)) — 별도 synthetic-only 경로는 "증명은 통과·실제 경로 미검증" 문제를 만듦. Pipeline: capture()→validateReplay()→classify()→buildFixture()→persist(destination).

## 3. promotion 부속 계약(33회차+)

- **dedup**: 같은 invariant+failure signature+root-cause class가 이미 존재하면 새 fixture 대신 `additional_reproducer`(primary_seed+additional_seeds)로 연결 — corpus 크기는 defect 수에 비례.
- **fixture identity는 의미 기반**(`auto-cut-undo-range-preservation.json`)·seed는 provenance 필드로 — "identity ≠ discovery mechanism"(BUG discovered_by와 같은 철학).
- **minimization**: 원본 candidate(seed·failing_step·full history) 보존+promoted_fixture(최소 시퀀스·derived_from_candidate) 연결 — 최소화가 provenance를 파괴하지 않게.
- **fail-fast**: 첫 deterministic failure에서 랜덤 run 중단→candidate 처리 후 다음 run(첫 결함의 side effect가 후속 실패를 만드는 것 방지).

## 4. 디스크 guard — START_GATE와 RUNTIME_GUARD 분리

- **START_GATE: BLOCK headroom ≥1GiB**(경계 근접 시 build/test 시작 금지 — "WARN이므로 소형 허용"이 0.29GiB로 안전성 판정을 하는 것 방지)·**RUNTIME_GUARD: raw<15GiB → 현재 atomic step 후 중단**.
- 장기: 작업 클래스 SMALL≥1GiB/MEDIUM≥5GiB/LARGE≥10GiB(수치는 실측 조정) — GO/WARN/BLOCK 하나로 모든 작업을 판정하는 것보다 안정적.

## 5. P3 semantic contract 3→4종

planner rejection 시 destructive best-effort guess 금지를 별도 invariant로: ①invalid action→no mutation ②**ambiguous plan→no destructive inference** ③replay→identical state ④serialization roundtrip→semantic-equivalent. 이번 100시나리오 측정의 플래너 결함 3건이 근거.

## 6. BUG-CORPUS-01 승인 시 child 분리

`BUG-CORPUS-01-FALLBACK`(retag/remux·성공 시 codec 경계 자체 소멸)과 `BUG-CORPUS-01-UX`(fallback 없어도 필요) 별개 — **구현 순서: fallback feasibility→behavior→final UX wording**(UX 문구를 먼저 고정하면 fallback 후 재수정). fallback 성공 시 UX는 "automatic compatibility conversion 실패 시" 표면으로 변화.

## 7. 32회차 closure 2종

- 디스크 회복 시: **PROMOTION_PIPELINE→synthetic failure captured→candidate generated→standalone replay FAIL→runner independence proved→injector removed→standalone replay PASS→candidate discarded→E2E CLOSED**.
- BLOCK 직전이면: contract/schema/path finalized→execution prerequisites ready→**GUARD_DEFERRED**(PARTIAL이 아니라 운영 판정의 결과).
- 성공 정의: "synthetic failure 잡음"이 아니라 stochastic discovery→evidence capture→deterministic standalone replay→promotion decision→immutable regression representation 체인의 단일 코드 경로 관통.
