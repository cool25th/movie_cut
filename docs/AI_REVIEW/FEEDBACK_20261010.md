#### ④의 cardinality 표기는 반드시 분리하십시오

원장에 a 하나가 존재하는 테스트를 기준으로, 다음처럼 기록하는 편이 정확합니다.

```
a 재등록:
dedup=true
matchesAfter(a)=1
registryTotal=1

새 candidate b 등록:
dedup=false
matchesBefore(b)=0
matchesAfter(b)=1
registryTotal=2
```

b → cardinality=2만 쓰면, "b와 일치하는 entry가 두 개"라는 중복 결함으로 읽힐 수 있습니다. P6에서 요구하는 1은 identity별 uniqueness이고, 2는 서로 다른 identity를 포함한 원장 전체 크기입니다.

또한 P1~P6와 5/5 PASS는 반드시 모순인 것은 아닙니다. 테스트 메서드 5개가 조건 6개를 검증할 수 있습니다. 다만 보고서에 조건 → 테스트 이름 → 핵심 assertion의 대응을 한 번 명시하십시오. 테스트 개수를 늘리라는 지시는 아닙니다.

### 2. ⑤: "self-confirming 아님"은 범위를 좁혀 표현해야 합니다

현재 설명에서 인정할 수 있는 부분은 다음입니다.

Identity 계산값의 일치만 확인하는 테스트는 아니다. 같은 fixture가 faulty dispatcher에서 표적 위반을 재현하고 clean dispatcher에서는 재현하지 않는 행동 증거가 있다.

그러나 여기서 곧바로 "identity 검증도 self-confirming이 아니다"라고 결론 내릴 수는 없습니다.

예를 들어 identity 함수가 중요한 상태 필드를 누락해도 replay는 정상 작동할 수 있습니다. 다른 두 fixture에서 idA ≠ idB가 성립하더라도, 동일한 의미의 candidate가 항상 같은 identity를 얻는지, 또는 특정 필드만 다른 별개 결함이 잘못 합쳐지는지는 별도 문제입니다. 이는 현재 테스트가 틀렸다는 지적이 아니라, 무엇을 증명했는지의 범위 구분입니다.

보고 문구는 다음으로 교정하는 것이 좋습니다.

> 재현 경로에는 faulty/clean 행동 대조가 있다. 다만 semantic identity의 정규화·필드 선택·해시 입력 정확성을 검증하는 독립 oracle은 아직 없으며, 현재 identity 검증은 제한된 dedup·분리 사례에 한정된다.

#### Golden 회귀 테스트 1건 등록으로 충분한가?

종료를 위한 후속 항목으로 1건 등록하는 것은 허용합니다. 다만 "해시 상수 하나와 현재 출력이 같다"만 확인하는 테스트로 끝내지는 마십시오.

기존 SeedPromotionProductionTests에 테이블 기반 테스트 하나로 다음 세 관계를 묶는 정도면 충분한 보강 범위입니다.

| 입력 | 확인할 관계 |
|---|---|
| 검토한 기준 candidate | 미리 확정한 canonical bytes 및 golden digest와 일치 |
| 의미는 같고 표현만 달라진 candidate | 기준 candidate와 같은 identity |
| 원인 command나 invariant 등 의미 필드가 달라진 candidate | 기준 candidate와 다른 identity |

두 번째 입력은 키 삽입 순서나 계약상 identity에서 제외하기로 한 관측 메타데이터만 바꾸면 됩니다. 실제 asset/source 의미나 상태 그래프의 연결 관계까지 제거해서는 안 됩니다.

핵심은 golden의 기대 canonical bytes를 운영 함수 출력으로 자동 생성하지 않는 것입니다. 작은 입력에 대해 명세를 읽고 기대 바이트를 검토한 뒤, 그 바이트의 digest를 별도 도구로 계산해 고정하십시오. 해싱의 반복 가능성에는 입력 표현의 불변성이 중요하므로, SHA-256 호출보다 그 앞의 정규화가 이번 검증의 중심입니다. (참고: RFC Editor)

정규화 계약에는 최소한 객체 키 순서, 숫자 표현, sequence 순서 보존을 명시하십시오. 참고로 RFC 8785는 객체 속성은 정렬하지만 배열 원소 순서는 바꾸지 않습니다. MovieCut의 command_sequence도 정렬 대상과 순서 보존 대상을 혼동하면 안 됩니다. RFC 전체를 지금 새로 도입하라는 뜻은 아닙니다.

후속 완료 시점은 다음 소형 검증 커밋으로 잡고, identity 알고리즘·스키마·자동 처리 범위를 변경하기 전에는 반드시 실행하십시오. "알고리즘이 바뀌면 언젠가 추가"로만 남기지는 않는 편이 좋습니다.

### 3. CLOSED까지 필요한 보완은 ⑥의 한 가지 수명주기 검증입니다

별도의 대규모 게이트를 만들 필요는 없습니다. 격리된 테스트 디렉터리에서 운영 저장 경로를 사용하는 테스트 한 건으로 다음을 확인하십시오.

```
candidate 캡처 및 실제 Registry writer로 저장
→ staging 디렉터리만 삭제
→ 기존 메모리 Registry 인스턴스 폐기
→ 디스크에서 새 Registry 인스턴스로 재로딩
→ 동일 identity와 provenance 7필드 확인
→ disposition에 맞는 영속 fixture/registry target 확인
```

중요한 구분은 두 가지입니다.

첫째, "기록이 남는다"와 "기록이 가리키는 증거를 사용할 수 있다"는 다릅니다. fixture 위치 문자열만 남고 대상 파일이 삭제됐다면, promoted fixture의 재현 가능성은 보존되지 않은 것입니다. PROMOTED나 기존 known fixture를 참조하는 entry라면, 정리 후에도 해당 영속 대상을 읽을 수 있어야 합니다.

둘째, 폐기한 합성 candidate까지 전부 영구 보존하라는 뜻은 아닙니다. 의도적으로 폐기한 항목은 그 disposition과 처리 이력이 남으면 됩니다. 이를 replay 가능한 promoted fixture처럼 표시하지만 않으면 됩니다. 합성 injector fixture의 자동 commit 금지와 명시적 promotion 원칙은 그대로 유지합니다.

#### 종료 승인 조건

⑥의 위 검증이 통과하고, 그 증거가 검증 대상 코드·테스트 버전에 연결되면 seed promotion wiring을 CLOSED로 기록해도 됩니다. ⑤는 알려진 한계와 후속 테스트로 남기십시오.

그때 같은 사안에 대해 다시 외부 판정 수신을 기다릴 필요는 없습니다. 이번 판정을 종료 조건에 대한 사전 승인으로 사용하면 됩니다. 반대로 검증을 실행하지 못했거나 실패했다면 FIXED_AWAITING_REVALIDATION을 유지하십시오.

### 4. 전체 진행에서 남은 리스크와 개선점

**A. 실측 SHA와 보고 HEAD를 분리해야 합니다**

보고에 등장하는 실측 근거는 d4a64f5, 44회차 HEAD는 832069b입니다. 이 차이 자체가 문제는 아니지만, "HEAD 유지"와 "현재 HEAD에서 PASS"는 다른 주장입니다.

두 커밋 사이가 문서 변경뿐이라면 기존 증거를 재사용할 수 있습니다. 반면 SeedPromotionSupport, 테스트, fixture, 빌드 설정 등 검증 결과에 영향을 줄 수 있는 부분을 보강했다면, 영향 범위의 재실측이 필요합니다.

다음 보고에서는 실측 SHA·실측 시각·보고 HEAD·증거 재사용 여부를 분리하십시오. 43회차의 여섯 항목 설명은 42회차 증거를 정리한 것이지, 여섯 항목을 새로 실행한 기록은 아닙니다.

**B. "3회 연속 ≥20GiB"의 집계 단위가 불명확합니다**

제시된 회차별 수치는 다음입니다.


따라서 42~44회차라는 세 회차 기준으로는 "3회 연속 ≥20"이 아닙니다.

다만 43회차의 직전 guard sample은 제시된 증감으로 계산하면 20.94GiB이므로, 회차가 아니라 guard sample 세 개를 뜻했다면 설명 가능합니다. consecutiveSamples인지 consecutiveLoops인지 구분하고 표본 시각을 남기십시오.

또한 10월 9일의 27.18GiB / GO는 10월 10일 작업 시작 허가를 대신하지 않습니다. 현재 guard와 작업 크기별 START_GATE를 다시 적용해야 합니다. RECOVERY_OBSERVED는 적절한 표현이며, 이를 디스크 문제의 근본 원인 해결로 확대하지 마십시오.

**C. Faulty/clean 대조의 "성공" 정의를 확인하십시오**

③은 인정하지만, 기존 assertion에서 다음 두 가지를 확인할 필요는 있습니다.

Faulty 쪽은 아무 오류가 아니라 의도한 invariant 위반을 검출해야 하고, clean 쪽은 명령을 실제 실행한 뒤 위반이 없어야 합니다. 디코딩 실패나 조기 종료가 faulty의 성공으로, 아무 명령도 처리하지 않은 상태가 clean의 성공으로 집계되면 대조군이 무력해집니다.

또한 "동일 fixture 인스턴스 사용" 자체가 장점은 아닙니다. 참조형 상태를 공유한다면 첫 실행의 변형이 두 번째 실행에 영향을 줄 수 있습니다. 동일한 immutable fixture 내용에서 각각 초기 상태를 구성하는 방식이 더 명확합니다. 새 테스트 수를 늘리기보다 기존 대조 테스트의 assertion과 상태 초기화를 확인하십시오.

**D. Registry 영속화에서는 cleanup 순서가 중요합니다**

성공 경로의 JSON round-trip과 별개로, 쓰기 실패 후 staging만 정리되는 경우는 후속 운영 리스크로 남습니다.

권장 원칙은 "영속 기록과 필요한 fixture 보존이 확인되기 전에는 성공 disposition을 확정하거나 staging을 정리하지 않는다"입니다. 단일 파일 저장에는 임시 파일에 쓴 뒤 원본을 교체하는 원자적 쓰기를 사용할 수 있습니다. Apple의 .atomic도 이러한 동작을 설명합니다. 다만 Registry 파일과 fixture 파일 각각을 원자적으로 저장했다고 두 파일 전체가 하나의 트랜잭션이 되는 것은 아니라는 점은 별도로 고려해야 합니다.

이 항목 때문에 지금 새로운 저장 시스템을 만들 필요는 없습니다. 우선 기존 writer의 실패 시 disposition과 cleanup 순서를 점검하고, 중단·실패 경로 보강을 후속으로 관리하십시오.

**E. 전송 장애가 전체 개발 중단으로 이어진 것은 프로세스 병목입니다**

44회차의 "판정 수신까지 신규 작업 병렬 착수 없음"은 너무 넓은 동결입니다.

Provenance를 보호하려면 검증 대상을 고정하면 되지, 프로젝트 전체를 멈출 필요는 없습니다. 검증 SHA와 증거를 고정하고, 해당 영역을 건드리지 않는 출시 준비를 별도 커밋이나 브랜치에서 진행하십시오.

다만 외부 응답이 없다는 이유로 승인받지 않은 promotion이나 배포를 수행해서는 안 됩니다. 구분은 다음과 같습니다.

승인이 필요한 변경은 대기한다. 이미 허용된 독립 작업은 진행한다. 전송 실패는 테스트 실패도, 프로젝트 전체 BLOCK도 아니다.

### 5. 이후 우선순위: release readiness가 먼저입니다

검증 인프라 중심의 반복에서 사용자 경로·출시 준비로 이동하는 방향은 승인합니다. 다만 "신규 AI Montage 개발부터 진행"으로 해석하지는 않겠습니다.

앞서 합의한 베타 우선·기능 확장 동결을 유지한다면, 순서는 다음이 적절합니다.

**우선: 출시 준비의 실제 증거 확보**

현재 베타 범위에서 설치 → 미디어 import → 편집 → Undo → 저장·재열기 → export → 결과 재생의 한 경로를 실제 기기와 배포 대상 빌드로 연결하십시오. 과거 Core 테스트 통과 수나 seed promotion의 PASS를 이 사용자 경로의 증거로 대체해서는 안 됩니다.

이전 기록의 Team ID·실기기·배포 대기 항목이 해소됐다는 증거는 이번 보고에 없습니다. 따라서 이를 임의로 PASS로 승계하지 말고 마지막 상태와 증거일을 유지하십시오. Apple의 TestFlight 배포는 개발자 프로그램과 배포 준비가 필요한 별도 경로입니다.

또한 빌드 생성, App Store Connect 업로드·처리 완료, 테스터의 실제 설치는 서로 다른 단계입니다. 업로드된 빌드는 Apple의 처리 과정을 거쳐야 하고, TestFlight에서는 테스터가 초대를 수락해 앱을 설치하는 단계까지 이어집니다. 출시 증거도 이 단계를 구분해 남기는 것이 맞습니다.

**다음: 이미 구현된 AI Montage 경로의 검증**

AI Montage가 이미 구현되어 베타 범위에 포함됐다면, 제안 확인 → 미리보기 → 적용 → Undo → 저장·재열기 → export를 사용자 경로로 검증하는 작업은 release readiness 아래에서 진행할 수 있습니다.

반면 아직 미배선된 신규 기능이라면, 베타 준비보다 앞세우지 마십시오. 이번 보고에는 기존 기능 동결 합의를 변경하거나 AI Montage의 신규 개발을 선행해야 할 근거가 없습니다.

**이후: 신규 AI 편집 능력 확대**

새 planner, 자동 편집 범위 확대, 고급 AI 기능은 베타의 실제 사용·복구·출력 증거를 확보한 뒤 진행하는 편이 기존 방향과 일치합니다.

**최종 지시**: ①~④는 보고 범위에서 인정하고, ⑤는 golden 보강 1건을 후속으로 수용합니다. ⑥의 실제 cleanup·재로딩 검증을 통과하면 wiring을 CLOSED로 전환하십시오. 그동안 전체 작업을 동결하지 말고, 신규 기능 확장보다 기존 사용자 경로와 release readiness를 우선 진행하십시오.

### 3. Golden identity 설계: 최소 후속 요건으로 충분

| 관계 | 검증할 내용 |
|---|---|
| 기준 candidate | 운영 canonical bytes가 수작업 기대 bytes와 같고, 운영 identity가 고정 digest와 같음 |
| 동일 의미·키 순서 변경 | 운영 입력 경로를 통과한 뒤 canonical bytes와 identity가 기준과 같음 |
| 의미 필드 변경 | canonical bytes와 identity가 기준과 다름 |

- **shasum -a 256 명시 필수**(shasum 기본은 SHA-1) — golden 확정 도구: `shasum -a 256 -b reviewed-canonical.json`. 파일 인코딩·말미 개행 포함 여부도 고정. 일반 테스트 실행마다 외부 shasum 호출 불필요(기대 bytes와 digest를 테스트 상수로 고정).
- 테스트가 운영 구현보다 먼저 입력을 정규화하지 말 것 — 키 순서 바꾼 입력을 실제 운영 입력 형식으로 넣어 운영 경로에서 정규화되게.
- 객체 키 순서와 command sequence 순서 구분 — 순서에 의미 있는 두 command의 순서를 바꾸는 입력으로 sequence 오정렬 결함도 겨냥. state/sequence/invariant 각 변경 사례는 같은 테이블에 추가 가능(별도 게이트 확장 불필요).
- 한계 명시: 이 테스트는 선택한 identity 규약과 사례의 회귀 방어 — 모든 입력에서의 올바름 증명 아님. golden 테스트 상수 등록=합성 fixture의 promotion corpus 자동 등록 승인 아님.
